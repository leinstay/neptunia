# メッセージとメモリ

ペルソナがメッセージを処理し、人々を記憶する仕組み。

## パイプライン

メッセージはギルド、チャンネル、自身のメッセージのフィルターを通過します。ペルソナが呼ばれた場合（@メンション、リプライ、名前トリガー）、無視ヒューリスティクスがベースの確率に対してロールし、素のピング、繰り返しタグ、スパム、発話者の関係スコアで調整されます。ベースの確率は、@メンションと本文でペルソナを @メンションしたリプライでは `mention.ignoreChance`、それ以外のペルソナへのリプライと、後述の分類器が `yes` と判定したフォローアップでは `mention.followUpIgnoreChance` です。名前トリガーは `mention.nameTriggerChance` だけでロールします。ロールに失敗した場合、メッセージは無視されます。無視されたメッセージは次のリプライ構築時にトランスクリプトに含まれます。

ペルソナが誰かに応答した後、そのチャンネルの次の `mention.followUpMinutes` 分間のタグなしメッセージは `analyzer` ロールの分類器に送られ、`yes`、`overheard` または `no` で応答します。`yes` はやり取りを続けます。`overheard`（ペルソナについての話、ペルソナに話しかけているのではない）は `mention.followUpOverheard` がオン（デフォルト）のとき `prompts/overheard.md` による独自のターンを開始し、オフのときは通常のフォローアップとして扱われます。3 回連続で `no`（`mention.followUpNoStreak`）が出るとウィンドウが閉じます。`overheard` は連続判定では `yes` としてカウントされます。フォローアップウィンドウは再起動後も維持されます。`features.followUp` でオフにできます。

自発的なターンはカオスタイマーまたはメッセージごとの盗み聞き確率（`spontaneous.eavesdropChance`）から発生します。全員に向けたメッセージ（特定の誰か宛てではない）は確率（`spontaneous.roomQuestionChance`、デフォルト 0.04）でペルソナに拾われます（分類器 `prompts/room.md` が事前フィルター）。そのターンはそのメッセージに焦点を合わせます。`spontaneous.deadAfterMinutes` の沈黙後、ペルソナ自身の最後のメッセージの後でも話題を切り出すことがあります。ペルソナは自身の最後のメッセージに対して割り込むことはありません。`spontaneous.maxChannelSilenceHours` 時間以上沈黙したチャンネルでは、ペルソナは自発的に発言しません。ただし直接のピングには応答します。

### 一度に一つ

ペルソナはサーバー全体で一度に一つのリプライを書きます（`mention.oneAtATime`）。`mention.pendingSameChannel` がオン（デフォルト `true`、キー欠落 = オン）のとき、ターン実行中の同じチャンネルに届いた直接ピング（@メンション、ペルソナのメッセージへのリプライ、または名前呼びかけ）は保留されます。ターン終了後に `mention.switchDelayMs` の待機で応答し、その時点で無視確率が判定されます。実行中のターンがそのピングをすでに履歴で処理済みの場合、二重に応答しません。スイッチオフの場合、ピングは見逃され、次のリプライのトランスクリプトに含まれるだけです。別のチャンネルからの直接ピングも同様に保留されます。すべての呼びかけは到着順に待機します。例外が 1 つあります: 保留フォローアップ（ビジー状態のターンに出くわした分類器の `yes`）はチャンネルごとに 1 件保持され、より新しいものが古いものを置き換えます。`mention.classifyWhileBusy` がオン（デフォルト）のとき、ペルソナがビジー中に届いたフォローアップ候補は分類器に送られ、保留フォローアップになることができます。スイッチオフの場合、候補は分類器呼び出しなしでスキップされます。ピックアップ時、保留フォローアップはメンションと同じチェックに加え 2 つの独自チェックを受けます: そのチャンネルのフォローアップウィンドウがまだ開いていること、およびその行がそのチャンネルで応答済みのターンの履歴に含まれていないこと。その後、`mention.followUpIgnoreChance` で無視確率のロールを受けます。`mention.pendingOverheard` がオン（デフォルト）の場合、ビジー中の分類器 `overheard` も保留キューで待機し、ペルソナは現在のターン終了後に反応します。待機中のフォローアップは後の overheard 行に押し出されません。待機中の overheard 行は後のフォローアップ、後の overheard 行、または直接メンション、リプライまたは名前呼びかけに押し出されます。待機中の overheard 行はスパム上限にカウントされず、チャンネルで待機中の呼びかけとして他のターンに報告されません。すべてのチャンネルと著者にわたって最大 `mention.maxPending`（デフォルト 6）件の呼びかけが保持されます。一杯になると最も古い 1 件が淘汰されます（`mention: dropped`、reason `full`）。呼びかけは `mention.pendingMinutes` 分後に期限切れになります。現在のリプライが完了すると、ペルソナは短いポーズ（`mention.switchDelayMs`）の後にチャンネルを切り替え、最も古い保留呼びかけにその時点の会話から応答します。通常の無視確率が適用されます。保留中の呼びかけはボットが一時停止中は応答されません。ビジー中の盗み聞きヒットはスキップされます。`mention.oneAtATime: false` の場合、チャンネルごとに独立して処理されます。ペルソナは Send Messages 権限がない場所では書き込みません。ただしそうしたチャンネルは読み取られ記憶されます。

呼びかけが届いた著者がそのチャンネルに待機中の項目をすでに持っている場合（分割メッセージのチェーンがまだ到達していないパートや、キューされた呼びかけ）、マージ分類器（`prompts/merge.md`、`analyzer` ロール、使用目的 `merge`）が新しいメッセージがそのうちの 1 つに属するかを判定します。属する場合、メッセージは独自の呼びかけとして待機する代わりにその項目に統合されます。統合されたメッセージはその項目のターンで `labels.task.added` を通じて表示されます。プロンプトファイルがない場合、すべての呼びかけは個別にキューされます。ログ: `merge: verdict`、`merge: failed`。

呼びかけに応答するターンは、同じ著者の他の待機中の呼びかけを `labels.task.queued`（分割ターンでは `labels.task.part` の `{others}` の一部）で示し、チャンネル内の他のメンバーの待機中の呼びかけを `labels.task.queuedOthers` で示します。この方法で示された呼びかけは、ターンの履歴に含まれていても「確認済み」として破棄されません。これらのラベルがない場合、従来のルールが適用されます。

`features.elsewhere` がオンの場合、読み取り専用チャンネルで呼ばれた（@メンション、リプライ、名前）呼びかけはそのチャンネルの会話が落ち着くのを待ち（`elsewhere.settleSeconds`、上限 `elsewhere.settleMaxSeconds`）、`memory.mainChannelIds` の最初の利用可能なチャンネルにジャンプリンク付きで応答します。通常の無視とスパムルールが適用されます。待機中はアテンションを占有しません。同じソースに新しい呼びかけがあると待機中のものと置き換わります（弱い場合を除く: タグの後の名前トリガー）。削除されたメッセージ（`gone`）やフェッチ失敗（`fetch-failed`）の呼びかけは破棄されます。待機中の再起動で呼びかけは失われます（リングに未回答として残る）。呼びかけはチャンネルごとのリング（`elsewhere.rememberPings`、デフォルト 20）に `elsewhere.pingMaxAgeDays`（デフォルト 7）日間記憶されます。ペルソナは読み取り専用チャンネルで読んだ内容について自発的にメインチャンネルでコメントすることもできます（`spontaneous: noticed` としてログ）。コメントには `prompts/elsewhere.md` がタスクとして使用されます。

### 分割メッセージ

`features.splitTasks` がオン（デフォルト）で、直接呼びかけ（メンション、リプライ、名前、フォローアップ、プライベートメッセージ）が十分に長く構造化されている場合（`split.minChars`、少なくとも 2 つのセパレーター）、分類器（`prompts/split.md`、`analyzer` ロール、使用目的 `split`）がそこに複数の独立したリクエストが含まれるかを判定します。分類器はターンの準備と並行して実行されるため、単一リクエストが遅延することはありません。回答は `one`（1 つのリクエスト）、または 2 件から `split.maxTasks` 件の行で、各行は `- ` で始まり著者自身の言葉でパートを示します。

パートは同じメッセージに対する通常のターンのチェーンとなります。各パートはそのターンのルックアップ、チャンネルルート、リコールヘルパーの候補となり、ペルソナのリクエストには応答中のパートと残りのパートが示されます（`labels.task.part`）。最初のパートはメッセージにリプライし、残りはプレーンで投稿されます。各パートには独自の期限とドロップバーがあります。ペルソナが沈黙、失敗、拒否で応答したパートは次のパートを止めません。一時停止またはウォームアップはチェーンを早期終了します（`turn: chain stopped`）。無視ロール、プライベートの日次上限、リングのスタンプはメッセージごとに 1 回カウントされます。チェーン実行中も保留中の呼びかけはキューに入り続けます。アテンションは最初のターンから最後まで保持されます。

設定: `features.splitTasks`、`split` グループ（`minChars`、`maxTasks`、`contextMessages`、`maxOutputTokens`）。`prompts/split.md` または `labels.task.part` がない場合、スプリッターはオフ。ログ: `split: verdict`、`split: skipped`、`split: failed`、`turn: part`、`turn: chain stopped`。

`features.pauseNotice` がオン（デフォルト）の場合、ペルソナが一時停止中に呼ばれると短い通知（`labels.limits.paused`）が投稿されます。チャンネルあたり `mention.pauseNoticeMinutes`（デフォルト 10）分に最大 1 回です。

### タイミング

ボイスリクエストの前に実行されるすべて（履歴、キャプション、ルートおよび検索分類器）には期限があります: `pace.prepareMs`（デフォルト 6 秒）、検索分類器の判定中と分類器が要求した検索の実行中は `pace.prepareSearchMs`（デフォルト 12 秒）に延長（「検索不要」の判定でホールドを即座に解除）、トリガーに説明モデルまたは動画ステージが処理するメディアが含まれる場合は `pace.prepareMediaMs`（デフォルト 20 秒）に延長。両方が適用される場合は大きい方が優先。期限を過ぎたヘルパーは破棄され、ターンはその結果なしで続行します（`turn: stage late` または `turn: stage failed` としてログ）。完成した回答自体はターン開始から `pace.dropAfterMs`（デフォルト 60 秒）以内に届く必要があります。過ぎた場合、ターンは投稿されず破棄されます（`turn: dropped` としてログ）。各ターンは `turn: timings` で各段階の所要時間をログに記録します。

`llm.hedge.roles`（デフォルト: `analyzer`、`reasoner`）にリストされたロールのリクエストはヘッジされます: 1 回目の `llm.hedge.afterMs`（デフォルト 2.5 秒）後に 2 回目の試行が開始され、先に完了した方が採用。どちらも開始から `llm.hedge.timeoutMs`（デフォルト 8 秒）で打ち切られます。`llm.helperTimeoutMs`（デフォルト 30 秒）はルート分類器、検索分類器、リコールサマリーを個別に制限します。

`pace.typingWhilePreparing` がオン（出荷時オフ）の場合、直接呼びかけに応答するターンの開始時点から入力中インジケーターが表示されます（完成した回答のタイプアウト中だけではなく）。

### リクエスト

ターンはチャンネルのトランスクリプトと隣接チャンネルを収集し、トークンバジェット内で一つの LLM リクエストを構築します。セクションは優先順に充填されます。システムプロンプトとタスクは決してカットされません。続いて発話者のプロファイル、ルックアップ結果（ウェブ、サーバー、またはその両方）、サーバーの傾向と自己言及、チャンネルマップ、ロアブックエントリ、トランスクリプト（新しい順）、他のプロファイル、隣接チャンネルの順です。

`features.channelRoute` がオン（デフォルト）の場合、分類器（`prompts/route-channel.md`）が会話の話題になっているチャンネルを最大 `route.maxChannels`（デフォルト 40）件の候補から選択し、そのチャンネルを `<channel_view>` ブロックとしてリクエストに取り込みます。明示的なチャンネルメンション（`features.channelPull`）と併用: ルート分類器は間接的な参照（「あのチャンネル」「Xのチャンネル」）を解決し、`<#id>` メンションは直接取り込まれます。

モデルにはサーバーのチャンネルマップ（目的、トピック、トーン、アクティビティレベル）が表示され、現在のチャンネルがマークされます。各チャンネルエントリにはコードが管理するファクトも含まれます: メッセージ数、最初と最後のメッセージ、30 日間のアクティビティヒストグラム、トップライター（`memory.channelWritersStored`、`memory.channelWritersHalfLifeDays` で減衰）。ウォームアップがチャンネルの履歴から充填し、ライブトラフィックが最新に保ちます。チャンネルのノートが `memory.notesStaleDays`（デフォルト 7）日以上古く、バッチにそのチャンネルから少なくとも `memory.notesBatchLines`（デフォルト 8）行あり、最後のノート変更またはレビュー以降に少なくとも `memory.notesMinMessages`（デフォルト 30）メッセージが蓄積し、前回のフラグから `memory.notesRetryHours`（デフォルト 24）時間以上経過している場合、アナライザーは陳腐化フラグを受け取り `note_reviews`（`updated`、`confirmed`、`insufficient_evidence`）で回答します。チェックとしてカウントされるのは確認されたレビューまたは実際のテキスト変更のみで、証拠不足や回答の欠落ではタイマーは継続します。

モデルは `<think>`（隠れた計画）、`<msg>`（1〜3 件のチャットメッセージ。`reply="#87"` でトランスクリプトの行にリプライ）、`<react>`（絵文字リアクション一つ）、`<skip/>`（沈黙）で応答します。解析後、人間の速度でタイピングがシミュレートされ、出力内の `@nick` が実際のメンションに変換されます。`/nep pings off` を設定したメンバーには、ペルソナのメッセージからの通知が届きません。リプライにピングは付かず、@メンションは表示されますが通知は送信されません。各メッセージは Discord の 2000 文字制限でカットされます。送信に失敗したメッセージはログに記録され（`turn: send failed`）、そのターンの投稿を終了します。

## 最近のノート

`features.recent` がオン（デフォルト）の場合、`<recent>` ブロックにサーバーで直近 `memory.recentHours`（デフォルト 72）時間に何が起きたかが表示されます: アナライザーが書く日付付きの短い行と、ターンが話しかけているメンバーの最近のエピソード。行はターン自身のチャンネル、またはここにいる全員が読めるチャンネルからのみ表示されます。プライベートチャットでは全サーバーメンバーが読めるチャンネルからのみ表示され、エピソードは含まれません。ターンが話しかけている人についての項目が優先されます。ブロックは `context.caps.recent`（デフォルト 1200）トークンで制限されます。

アナライザーはバッチごとに最大 `memory.maxNewRecent`（デフォルト 3）行、各 `memory.recentChars`（デフォルト 160）文字まで書きます。行は `data/guilds/<id>/recent.json` に保存され（最大 `memory.maxRecentStored`、デフォルト 150）、`memory.recentHours` 後に期限切れとなります。`/nep memory recent` でライブの行を確認できます。

## アナライザー

メモリアナライザーは十分なメッセージが蓄積した時点で別の LLM 呼び出しとして実行されます（`memory.batchMessages`、`memory.minBatchMessages`、`memory.maxBatchAgeMinutes`）。キャラクターカードを受け取り、キャラクターの目を通して各人を判断し、態度の変化、プロファイルの変更、チャンネルの観察、サーバーレベルのノートを返します。

バッチがトークン上限に対して大きすぎる場合、収まる最も古い行が分析され、残りは次のバッチに繰り延べられます（ログは `consumed`、`shown`、`deferred` を報告）。静かなプライベートバッファー（`memory.privateMaxAgeMinutes`、デフォルト 360 分間新しいメッセージなし）は `minBatchMessages` に達していなくても分析されます。内輪ネタと自己言及のリストは、リストが一杯のときに最も古い既存項目を淘汰して新しいエントリの余地を作ります。ロアは `lore.maxEntries` に達すると最も古いエントリを淘汰します。

失敗したバッチ（出力が途切れた、JSON がパースできない、トークン上限超過）は次の試行のバッチサイズを半分にします。バッチがフロア（20 メッセージ）でなお失敗する場合、即座にリトライせず 15 分待機します（`memory: update failed ... backing off` として `atFloor: true` と `backoffMs` 付きでログ）。バッファーはいずれの場合も保持されます。

### プロファイル

プロファイルは差分更新されます: アナライザーは変更があったものだけを返し、保存された事実が再要約されることはありません。各プロファイルには以下が含まれます:

- **キャラクターとスタイル**: ウォームアップ時にプロファイルプロンプト（`profile.md`）が全文を書き込む自由記述の段落で、コード（メッセージカウンターのスケジュール）またはアナライザーがギャップや矛盾を指摘した際にリフレッシュされます。ストリームアナライザーは直接編集しません。ストリームバッチからの `character` や `style` は破棄されます。
- **関心**: トピックとノートを持つアトミックな項目。頻度と新しさでランク付けされ、重みは時間とともに減衰します（`memory.interestHalfLifeDays`）。表示されるよりも多くの項目がメンバーごとに保持されるため（`memory.maxInterestsStored` vs `memory.maxInterests`）、新規項目は表示されない末尾で重みを蓄積できます。`memory.interestStaleDays` 以上目撃されていない関心は古いものとしてペルソナに表示されます。
- **詳細**: アトミックな項目（事実、特徴、コンテキスト情報）。関心と同じランキングと確定の仕組みで、独自の半減期（`memory.detailHalfLifeDays`）を持ちます。
- **エイリアス**: チャットの中で人々が実際にメンバーを呼ぶ名前。ペルソナは名前やエイリアスで言及されたメンバーが会話に参加していなくても認識します。
- **関係**: ペルソナとこの人がどういう関係にあるか。ペルソナの声で記述されます。
- **態度**: -100 から 100 のスコア（`features.relationships`）。アナライザーは小さな差分を返し、絶対スコアは設定しません。スコアはチャットに表示されません。ペルソナがどれだけ労力をかけるかに反映されます。`relationships.decayPerDay` が設定されている場合、スコアは毎日ゼロに向かってドリフトし、ゼロから遠いほど速くなります。relationship テキストは陳腐化すると書き直しフラグが立ちます: 段階変化（`relationships.bandHysteresis` ポイントの余裕付き）、記述時から `relationships.rewriteOnDrift` ポイントのドリフト、または `relationships.rewriteAfterMoves` 回の態度変動。テキストは `relationships.textChars`（デフォルト 600）文字に制限されます。

メンバーのキャラクターと話し方のポートレートは `memory.mainChannelIds` のチャンネルから作成されます。リストが空の場合はすべてのチャンネルが対象です。`memory.mainChannelIds` は読み取り専用チャンネルからの呼びかけへの応答先でもあります（`features.elsewhere`）。保存されたメモリはメンバーを ID で参照し、使用時に現在の名前が置換されるため、名前の変更で保存されたノートが壊れることはありません。

### 確定

関心と詳細は確定メカニズムを共有します。新しい項目は重み 1 で始まります（アナライザーが `"sure": false` をマークした場合は 0）。別の機会（少なくとも `memory.confirmGapHours` 間隔）に目撃されると重みが 1 上がります。項目は重みが `memory.confirmAfter` に達すると確定されます。それまではペルソナに「(未確定)」マーク付きで表示されます。エイリアスは同じランキングと目撃メカニズムを使用しますが、`"sure": false` メカニズムと未確定マークはエイリアスには適用されません。3 つすべてが `log2(weight + 0.5) + lastSeen / halfLife` でランク付けされるため、頻繁かつ最近のものが上位に来ます。

## エピソード

エピソードはペルソナが個々の人について記憶する出来事です: 侮辱、親切、約束、賭け、共有されたジョーク、ペルソナに何かを頼んだこと、あるいは決してしないよう頼んだこと。アナライザーは日付、短い説明、時にはその人自身の言葉、1 から 5 の重みとともにプロファイルに追記します。重いものほど長く残ります。プロファイルが `memory.maxEpisodes` に達すると、最も軽いものから先に削除され、次に最も古いものが削除されます。表示されるのは発話者のエピソードのみで、`<people>` ブロック内に含まれます。

## ロアブック

ロアブックはサーバー全体の知識を保存します。会話を超えて残るもの: イベント、繰り返し登場するキャラクター、長期にわたるストーリー、対立、伝統。各エントリにはタイトル、キーワードセット、短いテキスト（`lore.textChars`）があります。コードは直近の `lore.scanMessages` 件のメッセージをキーワードマッチでスキャンし、最大 `lore.maxMatches` エントリを `<lore>` ブロックに含めます。`always` とマークされたエントリは常に表示されます。マッチする少数だけが表示されるため、数百のエントリが存在してもコストはほぼゼロです。

アナライザーはロアブックエントリを追加・更新しますが、オーナーが `/nep lore` コマンドで追加したエントリには手を触れません。ロアブックデータは `data/guilds/<id>/lore.json` に保存されます。

日記は投稿履歴を `data/guilds/<id>/diary.json` に保持します（一行の要約、古い順、`diary.historyPosts` で上限）。[日記](diary.md)を参照。

アナライザーは、人々がペルソナに直接教えたこと（言葉や表現、サーバーに関する事実、振る舞いに関するリクエスト）もサーバーレベルのレッスンとして記録し、常にプロンプトに含まれます。

## プライベートレイヤー

`features.privateMessages` がオンの場合、ゲートを通過したメンバー（ギルドメンバーシップ、保存されたプロファイル、公開アフィニティが `private.minAffinity` 以上、本日のリプライ数がキャップ未満）が Discord DM でペルソナと会話できます。ペルソナは同じキャラクター、同じ公開メモリ。DM で話された内容はメンバーごとのプライベートレイヤーに保存されます。`features.privateLikeServer` がオン（デフォルト）の場合、DM はサーバーチャンネルのように動作します: ルート分類器、チャンネルプル、サーバー検索、言及メンバーのエピソードが利用可能で、DM パートナーが閲覧できるチャンネルに限定されます。

メンバーのプライベートレイヤーを確認できるのはボットオーナーのみです（`/nep memory private show`）。このコマンドは他のユーザーにグラントできません。

プライベートファイル `data/guilds/<guildId>/private/<userId>.json` は独自の `relationship`、`interests`、`details`、`episodes`、`affinity`（初期スコア 0）、日次リプライカウンター、観察バッファーを保存。他の会話には表示されず、サーバーバッチで書き込まれず、ディスク上の公開プロファイルと混合されません。

DM ではペルソナは公開とプライベートデータの結合を見ます: インタレストはトピックで結合（プライベートノートが優先）、ディテールは連結、エピソードは日付順。実効アフィニティは `clamp(公開 + プライベート, -100, 100)`。サーバーでは公開スコアのみ。

`/nep memory forget <user>` は公開プロファイルとプライベートファイルの両方を削除。`/nep memory wipe` はサーバーの `private/` ディレクトリ全体を削除。`/nep memory private forget <user>` はプライベートファイルのみを削除し、公開プロファイルは保持。

## ノートが長くなりすぎる場合

各プロースメモリフィールド（メンバーのキャラクター、スタイル、リレーションシップテキスト、チャンネルの目的・トピック・トーン、サーバーのパターンとスターター、ロアブックエントリのテキスト）には文字数制限がある。モデルが制限を超える置換テキストを書いた場合、新しいテキストは保存されない。古いテキストがそのまま残る。コードはモデルの書き換えを短縮しない。

ボイスモデル、ポートレートリフレッシュ、ノートリフレッシュは 1 回リトライを行う。リトライではモデルが自身の回答を受け取り、各フィールドの正確な文字数と制限を記したノートと共に、冗長な部分を削除して同じ内容を収めるよう求められる。短縮版が収まれば通常通り保存される。それでも収まらなければ古いテキストがそのまま残る。

ストリームアナライザーはリトライしない。バッチ内のフィールドが超過した場合、そのバッチの他の変更は適用される。スキップされるのはそのフィールドだけである。

唯一の例外は空のフィールドへの最初の書き込みである。保持すべき古いテキストがないため、モデルの回答は受け入れられ、文の境界で制限まで切り詰められる。

### 旧バージョン

`features.versions` がオン（デフォルト）の場合、プロースフィールドのテキストが置換されるたびに、以前のテキストが `data/guilds/<id>/versions/` に保存される。各レコードには日付、誰が書いたか（アナライザー、ボイスモデル、ポートレートリフレッシュ、ノートリフレッシュ、ウォームアップ、オーナー）、以前のテキスト、文レベルの比較が含まれる。

文の比較には 3 つの数値がある: `kept`（旧テキストと新テキストの両方に存在する文）、`removed`（旧テキストにあり新テキストにない文）、`added`（新テキストにあり旧テキストにない文）。`kept` が 0 で旧テキストに複数の文があった場合、モデルはマージせずにテキスト全体を置換した。バージョン履歴が捕捉するよう設計されているのはこの種の書き換えである。

フィールドあたり最大 `memory.versionsKept`（デフォルト 20）レコードが保持される。`/nep memory forget` でメンバーのバージョンファイルを削除。`/nep memory wipe` でサーバーの全バージョンファイルを削除。

## コマンド

全コマンドの一覧は[コマンド](owner-commands.md)にあります。メモリに関連する主なコマンド:

| コマンド | 動作 |
|---|---|
| `/nep memory recent` | ライブの最近のラインを表示 |
| `/nep memory show <user>` | 保存されたプロファイルのコンパクトな要約または特定のセクション |
| `/nep memory channel` | 保存されたチャンネルノートとコードが管理するファクト |
| `/nep memory server` | サーバー全体の傾向、内輪ネタ、自己言及 |
| `/nep memory refresh <user>` | メンバーのポートレートリフレッシュを強制実行 |
| `/nep memory forget <user>` | 保存されたプロファイルとプライベートメモリを削除 |
| `/nep memory affinity <user>` | 態度スコアと履歴の表示 |
| `/nep memory wipe` | サーバーのアナライザーメモリをすべて消去（プライベートファイル含む） |
| `/nep memory private show <user>` | メンバーのプライベートメモリを表示 |
| `/nep memory private forget <user>` | プライベートファイルのみを削除。公開プロファイルは保持 |
| `/nep lore add` | ロアブックエントリの追加または上書き |
| `/nep pause` / `/nep resume` | アクティビティを停止し、安全な手動編集のためにメモリをディスクにフラッシュ |
