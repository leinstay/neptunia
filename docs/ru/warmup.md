# Прогрев

Прогрев строит память персонажа о сервере из выборки недавних сообщений. Это инструмент администрирования, `tools/warmup.mjs`, запускается на сервере из директории бота с остановленным ботом, перед первым запуском (см. [Запуск](#запуск)). Слэш-команды для прогрева нет.

Бот никогда не запускает прогрев. Инструмент сам возобновляет незавершённый прогон.

## Этапы

Полный прогон проходит в фиксированном порядке: каналы, люди, сервер.

### Каналы

На каждый читаемый канал уходит один запрос; канал описывается по `warmup.messagesPerChannel` (по умолчанию 200) последним сообщениям независимо от их давности. Если история канала содержит меньше сообщений, бот пробует загрузить историю глубже. Канал без истории описывается только по названию, категории и теме. Результат: набор заметок о канале (назначение, темы, тон) и факты, которые ведёт код (количество сообщений, самые активные авторы, гистограмма активности за 30 дней).

### Люди

В прогрев попадают самые активные участники: не менее `warmup.minMessages` собственных сообщений за последние `warmup.lookbackDays` дней, до `warmup.maxPeople`, самые активные первыми. `node tools/warmup.mjs people` показывает подходящих участников при текущих настройках.

Для каждого подходящего участника движок выбирает до `warmup.messagesPerPerson` его сообщений с `warmup.contextBefore` строками окружающего контекста. На один канал приходится не больше `warmup.maxChannelShare` выборки. Большие выборки разбиваются хронологически на части, помещающиеся в `warmup.maxRequestTokens`; каждая часть после первой получает предыдущий ответ как блок `<draft>`, чтобы модель сохранила то, что подтвердилось, поправила изменившееся и дополнила новыми свидетельствами. Из финального ответа сохраняются характер, стиль, интересы, детали, эпизоды и псевдонимы; количество сообщений и временные метки первого/последнего появления вычисляются кодом.

### Сервер

Один запрос получает все заметки каналов, однострочную сводку по каждому профилированному участнику (имя, основные привычки, главные интересы) и `warmup.serverSampleMessages` (по умолчанию 600) последних строк основных каналов (`memory.mainChannelIds`; если пусто, учитываются все каналы). Результат сохраняется как серверные паттерны, зачины разговоров, внутренние шутки и записи лорбука.

## Охват

Прогрев записывает: заметки каналов (назначение, темы, тон), профили участников (характер, стиль, интересы, детали, эпизоды, псевдонимы), серверные привычки (паттерны, зачины разговоров, внутренние шутки) и лорбук.

Отношение (балл) и поле `relationship` при прогреве не заполняются. Они растут только из живого общения через потоковый анализатор.

`character` и `style` это прозаические поля, их пишет только промпт профиля (`profile.md`), как при прогреве, так и при обновлении портрета. Потоковый анализатор никогда не редактирует их напрямую. Модель данных и схема вывода описаны в [контракте промптов](prompt-contract.md).

## Прогресс

Прогресс сохраняется в `state.warmup` в `data/state.json` после каждого запроса и переживает перезапуски. Прогон, прерванный по Ctrl+C, бюджетом токенов, ограничением частоты или тремя неудачными запросами подряд, продолжается с места остановки при повторном вызове `node tools/warmup.mjs run`. `node tools/warmup.mjs reset` очищает только прогресс, не сохранённую память.

## Ограничения

Общий бюджет токенов на прогон: `warmup.maxTokens` (по умолчанию 6 000 000). Каждый запрос ограничен `warmup.maxRequestTokens` (по умолчанию 120 000, вход плюс выход) и `warmup.maxOutputTokens` (по умолчанию 6 000 выход). При сборе пула выборки из каждого канала читается до `warmup.fetchLimitPerChannel` (по умолчанию 15 000) сообщений.

При получении HTTP 429 от провайдера прогрев ждёт `warmup.rateLimitWaitMinutes` (по умолчанию 10) минут и повторяет попытку. После `warmup.rateLimitMaxWaits` (по умолчанию 36) последовательных ожиданий прогон прерывается; прогресс сохраняется и прогон можно возобновить.

## Обновление портрета

После завершения прогрева потоковый анализатор обновляет память по живым батчам. Портреты обновляются двумя способами.

**По счётчикам** (`features.portraitRefresh`). Периодический планировщик проверяет каждые `memory.portraitCheckMinutes` (по умолчанию 60) минут, кто из участников написал минимум `memory.portraitRefreshMessages` (по умолчанию 300) собственных сообщений с момента последнего портрета И чей последний успешный рефреш был хотя бы `memory.portraitRefreshDays` (по умолчанию 3) дня назад. В день обновляется до `memory.portraitRefreshPerDay` (по умолчанию 3) участников, начиная с самых активных. У участника без портретной метки подсчитываются все сообщения, поэтому после деплоя несколько человек окажутся на очереди одновременно; дневной лимит распределяет их. Неудачная попытка ждёт `memory.portraitRetryHours` (по умолчанию 24) часов. Выборка вписывается под 50k-рельс по токенам.

**По подсказке анализатора.** Когда потоковый анализатор замечает повторяющуюся привычку или изменение в манере письма участника, которые сохранённый портрет упускает или которым противоречит, он возвращает однострочную подсказку, и код ставит обновление в очередь. Этот путь использует существующий кулдаун `memory.portraitRefreshHours` (по умолчанию 24 ч) на участника. Потоковый анализатор больше не может перезаписывать `character` или `style` напрямую.

В двухэтапном режиме обновление портрета не запускается, пока у участника ожидается голосовой элемент character (`voice-pending`). Принудительное обновление (`/nep memory refresh`) обходит эту проверку. `/nep memory refresh` сообщает владельцу, если у участника есть элемент character в очереди.

Оба пути делят дневной лимит. `/nep memory refresh <user>` запускает обновление независимо от таймеров, но также расходует лимит. Каждое обновление учитывается в `llm.maxRequestsPerDay`.

При обновлении `profile.md` вызывается с сохранённым портретом как `<draft>` и заметкой анализатора как `<hint>` (если есть). Черновик используется для слияния: всё, что ещё соответствует выборке, сохраняется (сжимается для экономии места), противоречащее пересматривается, новые повторяющиеся привычки добавляются, а пункт, который выборка просто не показывает, НЕ удаляется. Новые характер и стиль заменяют сохранённые; интересы, детали, эпизоды и псевдонимы из ответа отбрасываются.

## Запуск

Инструмент запускается из директории бота, от имени сервисного пользователя, с остановленным ботом:

```bash
sudo systemctl stop neptunia-bot
cd /opt/neptunia-bot
sudo -u neptunia-bot node tools/warmup.mjs run --guild <server id> --dry-run
sudo -u neptunia-bot node tools/warmup.mjs run --guild <server id> --spend <usd>
sudo systemctl start neptunia-bot
```

`--guild` можно не указывать, когда `data/guilds/` содержит ровно один сервер или когда задан `bot.guildId`. Инструмент читает `config.json`, `config.local.json`, `prompts/`, `prompts.local/` и `.env` из директории бота, получает историю Discord по REST через токен бота (без gateway-сессии, ничего не публикуется) и отправляет запросы к модели через ключ OpenRouter.

| Подкоманда | Что делает | Расходует |
|---|---|---|
| `run` | Все читаемые каналы, все подходящие участники и серверные заметки, которые прогресс ещё не записал, в этом порядке | да |
| `users [--user <id>]` | Построить профиль указанного участника или всех подходящих, независимо от прогресса | да |
| `channels [--channel <id>]` | Описать указанный канал или все читаемые | да |
| `server` | Пересобрать серверные заметки и лорбук | да |
| `people` | Список подходящих участников | нет |
| `status` | Фаза, прогресс, расход токенов относительно `warmup.maxTokens` | нет |
| `reset` | Очистить только прогресс, не сохранённую память | нет |

**Расход.** `run`, `users`, `channels` и `server` сначала печатают план (каналы, участники, серверные заметки) и оценку, и отклоняются с кодом выхода 2, если `--spend <usd>` не покрывает оценку. Оценка считает каждый запрос по `warmup.maxRequestTokens`, в рамках остатка от `warmup.maxTokens` и `--max-usd <n>` (если указан), по цене `--usd-per-ktok` (по умолчанию 0.005 USD за тысячу токенов). Далее прогон использует эту оценку как бюджет: останавливается на ней (можно возобновить) и никогда не тратит больше. У участника, чья выборка не помещается в один запрос, бюджет может исчерпаться раньше; запустите снова для продолжения. `--dry-run` печатает план и оценку, ничего не отправляя. Запросы никогда не учитываются в `llm.maxRequestsPerDay`.

**Безопасность.** `run`, `users`, `channels`, `server` и `reset` отклоняются, пока бот работает на этом `data/` (маркер `.running` в журнале) и указывают `sudo systemctl stop neptunia-bot`. Расходующие подкоманды также отклоняются, пока идёт удаление пользователя, отклоняются пока память на паузе и первым делом применяют книгу удалений, когда `data/` ещё содержит то, что она убирает. `people`, `status` и пробные запуски ничего не записывают. Ctrl+C отменяет текущий запрос и останавливает прогон; прогресс сохраняется. Перед выходом инструмент сбрасывает память на диск, включая копии архива.

**Что записывается.** Заметки и факты каналов в `data/guilds/<id>/channels/`, профили участников в `data/guilds/<id>/users/`, серверные заметки в `data/guilds/<id>/guild.json`, лорбук в `data/guilds/<id>/lore.json`, прогресс в `data/state.json`; при включённом `features.archive` то, что перезапись вытесняет, сначала уходит в архив.

**Далее.** Запустите бот. С этого момента память обновляется ботом: потоковый анализатор по живым батчам, обновление портрета и обновление заметок (ниже). `/nep memory refresh kind:user <user>` перезаписывает портрет одного участника; `kind:channel <channel>` и `kind:server` перезаписывают заметки канала или серверные заметки из свежей выборки, тот же запрос, что и при обновлении заметок ниже, под живыми ограничениями, с говорящим персонажем. Канал без заметок и лорбук остаются за инструментом: `channels --channel <id>` и `server`.

Для полностью чистого старта сначала выполните `/nep memory wipe`: команда очищает профили участников с их отношениями и эпизодами, серверные привычки, карту каналов, записи лорбука и прогресс прогрева.

## Актуализация заметок

Заметки каналов и сервера записываются при прогреве, затем обновляются потоковым анализатором, когда в батче достаточно свидетельств. Со временем, однако, короткие батчи не замечают постепенных сдвигов в том, как люди общаются или о чём канал. Обновление заметок по выборке (`features.notesRefresh`) ловит это, периодически перепроверяя заметки на полной выборке недавних сообщений, так же, как при прогреве канал описывался изначально.

### Что происходит

Планировщик проверяет каждые `memory.notesCheckMinutes` (по умолчанию 60) минут, какие каналы и серверные заметки просрочены. Канал считается просроченным, когда: у него уже есть текст заметок (канал, который прогрев не описал, остаётся за прогревом); прошло достаточно дней с последнего изменения текста или последней проверки по выборке (`memory.notesRefreshDaysMain`, по умолчанию 7 для каналов из `memory.mainChannelIds`, или `memory.notesRefreshDays`, по умолчанию 21 для остальных); подсчитано минимум `memory.notesMinMessages` (по умолчанию 30) сообщений с тех пор; в канале было сообщение в пределах `warmup.lookbackDays` (по умолчанию 60) дней; и не было неудачной попытки в пределах `memory.notesRetryHours` (по умолчанию 24).

Для просроченного канала движок читает `memory.notesSampleDays` (по умолчанию 30) дней истории, отбрасывает строки персонажа и других ботов и выбирает `memory.notesSampleMessages` (по умолчанию 160) сообщений, распределённых по дням. Распределение избегает перепредставления последнего разговора: движок берёт по одному сообщению на день за раунд, сначала новейший день, и один автор может занимать не более `memory.notesSampleMaxAuthorShare` (по умолчанию 0.35) выборки. Если пригодных сообщений меньше `notesMinMessages`, канал пропускается (`too-few`).

Запрос использует тот же `channel.md` (или `server.md` для сервера), что и при прогреве, с одним дополнением: блок `<existing_notes>` с сохранёнными заметками в виде JSON и `writtenDaysAgo` (целые дни с последнего изменения, null при неизвестности). Промпт указывает модели рассматривать их как гипотезы для проверки по выборке, а не как свидетельства. Ответ заменяет сохранённые назначение, темы и тон (или паттерны, зачины и внутренние шутки для сервера). Если текст канала изменился между чтением истории и получением ответа (другой батч обновил его), ответ отбрасывается (`conflict`). В любом случае валидный ответ проставляет `notesSampleReviewedAt`. `updatedAt` текста сдвигается только при реальном изменении.

Сервер следует тому же правилу: `memory.notesServerRefreshDays` (по умолчанию 7) с последнего изменения или проверки, минимум `memory.notesGuildMinMessages` (по умолчанию 100) сообщений суммарно по всем каналам. Сервер идёт после каналов в цикле и не учитывается в дневном лимите каналов.

### Как часто, чем это стоит

До `memory.notesRefreshPerDay` (по умолчанию 4) успешных обновлений каналов за UTC-сутки. Неудачный запрос не занимает слот. Дневной счётчик хранится в `state.json` как `notesRefreshDay` / `notesRefreshCount`. Обновления сервера не учитываются в лимите каналов.

Каждый запрос обновления учитывается в `llm.maxRequestsPerDay` и 50k-рельсе по токенам, но не в бюджете прогрева `warmup.maxTokens`. Персонаж не замолкает на время обновления. Обновление отклоняется, пока идёт прогрев.

### Строки лога

`warmup: notes refreshed` с `{ target: "channel" | "server", channelId, changed, sample, authors, days }`.

`warmup: notes refresh failed` с `{ target, channelId, reason }`. Причины: `running` (прогрев идёт), `paused`, `gone` (канал больше не существует), `too-few` (слишком мало пригодных сообщений), `conflict` (текст изменился между чтением истории и ответом), `bad-json`, `llm-error`, `token-limit`, `daily-cap`, `no-prompt`.

`notes refresh: look` с `{ due, started, refreshed, changed, skipped }` и `buckets { neverReviewed, fresh, due, few, quiet, retryWait }` по всем каналам.

Ничего не переписывается ради видимости свежести. Когда выборка не может определить, актуальна ли формулировка, сохранённый текст остаётся как есть.

Полный список ключей конфигурации прогрева: [Конфигурация: `warmup`](configuration.md#warmup).
