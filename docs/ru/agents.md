# Агенты-посыльные

Движок может поручить задачу отдельному агенту-посыльному: самостоятельному процессу, который выполняет одно дело (поиск в интернете, чтение локальной файловой системы) и возвращает результат. Каждый агент работает как воркер [OpenCode](https://opencode.ai), управляемый кодом раннера в `src/agent-runner/`. Он не импортирует бота и работает на собственном ключе OpenRouter, а не на ключе персонажа. Движок поставляется с двумя профилями воркеров:

| Профиль | Что делает | К чему имеет доступ | Инструменты |
|---|---|---|---|
| `web` | интернет-поручения (поиск, чтение страниц, просмотр изображений, скачивание файла) | публичный интернет через прокси; собственная папка вывода | OpenCode `websearch`, `webfetch`, `read` и `bash`, ограниченный `curl`/`wget`/`ffmpeg`/`ffprobe`/`file`/`ls`/`mkdir` для скачивания |
| `server` | вопросы к этой машине в режиме только для чтения | локальная файловая система (только чтение); сеть только до API модели | OpenCode `read`, `grep`, `glob`, `list` и `bash`, ограниченный командами только для чтения (`ls`, `cat`, `head`, `tail`, `grep`, `find`, `ps`, `systemctl status`, `journalctl`, `df`, `du`, `stat`, `git log`, ...) |

Оба выполняют задачи по одной; остальные запросы ставятся в очередь. Каждая задача имеет индивидуальные лимиты (`agents.<profile>.limits`: шаги модели, ориентировочная стоимость в USD, время выполнения) и дневные лимиты (`agents.<profile>.daily`). Лимит USD — мягкий лимит на оценку стоимости OpenCode; жёсткий лимит расходов — кредитный лимит ключа OpenRouter раннера.

## Папка agents

Каждый агент живёт в своей папке внутри `agents/` в корне движка: `agents/web/` и `agents/server/` — два воркера, `agents/advice/` — консультация. Папка содержит отслеживаемый промпт агента (`prompt.md`) и его описание (`profile.json`). Раннер строит профили из этой папки при запуске (`src/agent-runner/profiles.js#loadProfiles`); бот читает ту же папку для значений по умолчанию (сокет, папка вывода, лимиты, дневные лимиты). `listAgents` возвращает всех агентов, воркеров и консультации.

Два вида агентов. Воркер запускается как отдельный процесс (`bin/agent-runner.mjs --profile <id>`) и принимает задачи через Unix-сокет. Консультация не имеет процесса: инструменты вызывают её модельную роль напрямую. Раннер пропускает консультации.

## Ключи профиля

`profile.json` описывает, что агент запрашивает; он ничего не авторизует. Все ключи обязательны:

| Ключ | Содержимое |
|---|---|
| `id` | имя папки (`web`) |
| `kind` | `worker` (запускается под раннером на сокете) или `consultation` (модельная роль, которую инструменты вызывают напрямую; без процесса, раннер пропускает) |
| `role` | модельная роль в `src/llm/roles.js` (`agent.web`, `agent.server`, `agent.advice`) |
| `prompt` | файл промпта внутри папки (`prompt.md`); `null` для консультации без промпта |
| `override` | имя файла, который деплоймент может положить в `prompts.local/` для замены промпта (`agent-web.md`); `null` если промпта нет |
| `description` | одно предложение о том, что делает агент |
| `tools` | только для воркера: инструменты OpenCode, которые он запрашивает, не более тех, что разрешает его класс оболочки |
| `shell` | только для воркера: имя класса оболочки, определённого в коде раннера (`server-read-only`, `web-download`) |
| `limits` | только для воркера: лимиты по умолчанию на задачу `{ steps, usd, seconds }`, переопределяемые `agents.<id>.limits` в конфигурации |
| `daily` | только для воркера: дневные лимиты по умолчанию `{ tasks, usd }`, переопределяемые `agents.<id>.daily` |
| `searchProvider` | только для воркера: провайдер веб-поиска по умолчанию (`exa`) или `null` |
| `socket`, `out` | только для воркера: путь сокета и папка вывода по умолчанию, переопределяемые `agents.<id>.socket` / `.out` |
| `env` | только для воркера: имена переменных окружения, к которым раннер обращается, если задача не принесла ключ |

Профиль с отсутствующим ключом, неизвестным ключом, инструментом, который не разрешает его класс оболочки, или неизвестным классом оболочки останавливает раннер (и бота, читающего ту же папку) при запуске с одной строкой ошибки, называющей агента и ключ.

## Что не указывается в профиле

Разрешения и безопасность остаются в коде (`src/agent-runner/profiles.js`, `src/agent-runner/policy.js`), и никакой ключ профиля не может их изменить:

- потолок разрешений: какие инструменты может выдать класс оболочки и какие команды оболочки он разрешает;
- шаблоны запрета оболочки и инструменты, запрещённые каждому агенту (`edit`, `write`, `patch`, `task`, `question`); `external_directory` (пути вне собственной папки агента) также запрещён, за исключением серверного агента, который получает его с теми же правилами скрытых путей, что и его файловые инструменты;
- фильтры области видимости, скрытые пути и редакция результатов;
- любая команда на выполнение и любой путь за пределами папки (`socket` и `out` — только значения по умолчанию, которые переопределяет конфигурация).

Профиль может только сузить то, что разрешает код: инструмент, который профиль не указал, запрещён. Инструмент, который не разрешает его класс оболочки, или неизвестный класс оболочки отклоняется при запуске.

## Два сервиса

Каждый воркер работает как отдельный сервис systemd и пользователь Unix (`deploy/neptunia-agent-web.service`, `deploy/neptunia-agent-server.service`; инструкции по установке в заголовках юнитов):

- `neptunia-agent-web`: имеет сеть; исходящий трафик к localhost и приватным диапазонам запрещён юнитом (`IPAddressDeny=`) и в коде. Файловая система доступна только для чтения, за исключением его каталога состояния (`ProtectSystem=strict`, `ProtectHome=yes`, `InaccessiblePaths=` для `/srv`, данных бота и `.env`, `/var/www`, nginx и Let's Encrypt).
- `neptunia-agent-server`: сеть только к локальному резолверу и API модели (`IPAddressDeny=any` плюс `IPAddressAllow=` для диапазонов Cloudflare, где живёт OpenRouter; оболочка также запрещает `find -exec`, сетевые пути `awk` и `gawk` поверх allow-листа). Вся система доступна только для чтения (`ProtectSystem=strict`, нет путей для записи кроме его каталога состояния и приватного `/tmp`); его единственная команда записи, `cp`, может скопировать файл только в папку задачи, откуда он возвращается как файл результата, а в фильтрованной области скрытый путь отклоняется для `cp` так же, как для `cat`. У него есть `CAP_DAC_READ_SEARCH`, позволяющий читать любой файл без root. Гарантия только для чтения обеспечивается юнитом, а не фильтром команд.

Оба запускаются через `bin/agent-runner.mjs --profile <name>`. Они читают лимиты, стоимость модели и сокет из `agents.<profile>` в конфигурации, а модель — из модельных ролей `agent.web` и `agent.server` (устанавливается через `/nep model set`, перечитывается для каждой задачи; `run` может нести собственную `model`). Настройки: [Конфигурация: `agents`](configuration.md#agents).

## Ключи

Все ключи хранятся в ядре, в файле `.env` бота, который раннеры (непривилегированные, с недоступным для них файлом) прочитать не могут. Ядро отправляет ключи с каждой задачей в `secrets` сообщения `run`.

Ключ OpenRouter — ключ модельной роли задачи, разрешённый так же, как бот разрешает ключ любой роли (`llm.keyByRole`): `agent.web` и `agent.server` используют `OPENROUTER_AGENT_KEY`; без этой переменной секреты не отправляются. Бот никогда не отправляет собственных запросов на ключах агентов. Агент `web` также получает прокси (`MEDIA_VIDEO_PROXY`, отправляемый как `http://`-URL, который прокси тоже обслуживает) и `OPENCODE_WEBSEARCH_KEY` при наличии. Раннер передаёт дочернему процессу OpenCode ключ как `OPENROUTER_API_KEY`, прокси как `HTTPS_PROXY` / `HTTP_PROXY` (и их строчные формы, которые читает curl), а ключ поиска — провайдеру поиска.

`EnvironmentFile` юнита (`/etc/neptunia/agent-<profile>.env`, принадлежит root, 0600) необязателен: его `OPENROUTER_AGENT_KEY`, `OPENCODE_WEBSEARCH_KEY` и `PROXY_URL` используются только для того, что задача не принесла. Задача без ключа из обоих источников завершается с `no-key`, с одним предупреждением на раннер. Никакой секрет не логируется, не попадает в журнал и не возвращается в событии.

Карточка `/nep status` владельца показывает ключ агентов как ключ `agents`, а `OPENROUTER_DEV_KEY` кодингового воркера (роль `agent.dev`) как ключ `development`. Четвёртая роль агента, `agent.advice`, задаёт модель инструментов консультации вне бота (голый id OpenRouter, на `OPENROUTER_SIM_KEY` симулятора); никакой агент-посыльный и никакой запрос бота её не использует.

## Протокол

Ядро подключается к Unix-сокету раннера (`agents.<profile>.socket`, группа `neptunia-discord-interface`, режим 0660) и обменивается JSON, по одному объекту на строку (`src/agent-runner/protocol.js`).

Ядро к раннеру:

- `{ "op": "run", "id", "goal", "context": { "scope", "channel", "asker", ... }, "limits": { "steps", "usd", "seconds" }, "tools": [...], "model"?, "cost"?, "searchProvider"?, "secrets"?: { "openrouterKey", "proxy"?, "searchKey"? }, "preamble"? }` (`secrets`: непустые строки, других ключей нет; отклонённый `run` получает в ответ только код ошибки, без значений; `preamble`: общая преамбула (см. ниже), строка не более 8000 символов после обрезки пробелов, иначе run отклоняется с `bad-preamble` или `preamble-too-long`)
- `{ "op": "cancel", "id" }`
- `{ "op": "ping", "ids": [...] }`

Раннер к ядру:

- `{ "id", "event": "progress", "step", "tool", "note" }` по ходу работы;
- один `{ "id", "event": "end", "status": "done" | "failed" | "cancelled", "result": { "text", "sources": [url...], "files": [{ "path", "name", "contentType", "bytes" }], "withheld"?: [path...], "filesDropped"?: [{ "name", "reason" }] }, "usage": { "input", "output", "usd", "steps", "seconds", "costUnknown"? }, "error"? }` (`withheld`: пути, в которых агенту было отказано в фильтрованной области, не более 50; `filesDropped`: файлы результата, которые раннер не доставил, причина `withheld`, когда запуск в фильтрованной области обратился к скрытому пути (тогда ни один файл не доставляется), или `secret`, когда текстовый файл не более 2 МБ содержит секрет, в любой области);
- `{ "event": "pong", "profile", "busy", "queued" }` в ответ на `ping`.

Раннер, перезапустившийся после сбоя, отвечает `end` со `status: "failed", error: "restarted"` на любой id из `ping`, который он больше не знает, чтобы ядро перестало ждать. По `SIGTERM` раннер завершает каждую открытую задачу таким же образом и завершается. Выходные файлы попадают в `<out>/<id>/`, и ядро удаляет их через `agents.keepFilesHours`.

## Область видимости и редакция

`run` несёт `context.scope`, одно из `core`, `dm`, `group` (`src/agent-runner/policy.js`). В `core` ничего не скрывается. В `dm` и `group`:

- файловые инструменты агента `server` запрещают содержимое чувствительных путей (`/var/www`, любые `.git`/`.local.git`, `.secrets`, `.env`, `.ssh`, `/etc/shadow`, nginx htpasswd, Let's Encrypt, `/etc/neptunia`, `/srv/neptunia-backups`, `config.local.json`, `data/` самого персонажа и любые `.agents/scratch`), а его `bash` запрещает команды просмотра содержимого (`cat`, `head`, `tail`, `grep`, `egrep`, `fgrep`, `sed`, `awk`, `cut`, `sort`, `uniq`, `wc`, `file`, `git`) с аргументом, указывающим на один из этих путей. Команды для вывода имён (`ls`, `find`, `stat`, `du`, `readlink`, `realpath`) по-прежнему разрешены. Отказ происходит на уровне шага: OpenCode отклоняет этот один вызов инструмента, агент видит отказ и продолжает, а `withheld` результата перечисляет пути, в которых ему было отказано;
- каждый результат, возвращаемый раннером, проходит проход редакции, заменяющий строки, похожие на ключи, токены и пароли, блоки приватных ключей, материал SSH-ключей и учётные данные URL на `[redacted]`.

Команда, которая добирается до скрытого пути несмотря на эти правила (через `bash -c`, через пайп в ридер), перехватывается постфактум: раннер не сохраняет этот вывод (его событие прогресса сообщает `withheld` и путь), путь добавляется в `withheld` результата, и задача продолжается. Агент видел вывод, поэтому финальный проход редакции — это то, что не даёт секрету попасть в ответ.

## Как выполняется задача

Каждая задача — один дочерний процесс `opencode run` в новой рабочей директории внутри папки вывода профиля, с отключёнными проектной и `.claude`-конфигурацией, автообновлением и загрузкой каталога цен, чтобы ничто с этого сервера не утекло в воркер. Движок формирует конфигурацию OpenCode (промпт агента из `agents/<profile>/prompt.md` или из `prompts.local/agent-<profile>.md` деплоймента при его наличии, лимит шагов, набор разрешений для области видимости, модель и её стоимость) и передаёт через `OPENCODE_CONFIG_CONTENT`. Дочерний процесс выводит поток JSON-событий; раннер суммирует стоимость и токены за шаг, пересылает прогресс, берёт финальный текст ассистента как результат, перечисляет файлы, сохранённые агентом, и останавливает дочерний процесс при достижении лимита. Собрано на OpenCode v1.19.3.

Развёртывание может дать каждому агенту-посыльному одну общую преамбулу: необязательный файл `prompts.local/agents.md` (отслеживаемого дефолта нет; без файла или с пустым файлом ничего не меняется). Ядро читает его через живой загрузчик промптов, поэтому правка дойдёт до следующей задачи без перезапуска, и отправляет текст с каждой задачей как `preamble` сообщения `run`. Раннер ставит его первым в системном промпте агента, за ним пустая строка и собственный промпт агента. Раннеры не читают `prompts.local/` для получения преамбулы: файл читает только ядро, поэтому раннер, чей юнит не пускает его к приватной директории, всё равно получает преамбулу. Преамбула не логируется; строка `errands: sent` ядра содержит только её длину.

## Сторона персонажа

Ядро (`src/errands/`) хранит задачи персонажа на сервере в `data/guilds/<id>/tasks.json` (открытые и последние завершённые) и `tasks.jsonl` (одна строка на переход), и журналирует каждый переход как одну операцию `task` (только счётчики, без текста цели или результата). Задача проходит состояния `queued`, `running`, затем `done`, `failed` или `cancelled`.

- Операции (также навыки персонажа, закрытые до выдачи; см. [Команды](owner-commands.md#member-commands)): `task.run` (`agent`, `goal`; платно), `task.status` (`id` необязателен), `task.cancel` (`id`), `task.list`. Любой участник может попросить `web`; только владелец может попросить `server`, через персонажа или напрямую. `task.run` немедленно отвечает с id и `queued`, задача выполняется в фоне с лимитами `agents.<profile>.limits`. Задача из приватного чата выполняется в области `dm`, остальные в `group`. Ограничения: `agents.maxOpen` открытых задач и `agents.<profile>.daily` за UTC-сутки.
- `<tasks>`: в хвосте каждого запроса, пока у персонажа есть открытая задача или завершённая, которую персонаж ещё не видел, по одной строке (id, агент, состояние, возраст в минутах, цель, обрезанная до 120 символов). Задачи приватного чата показываются только в этом чате. Завершённая задача считается увиденной после хода персонажа, который её показал.
- `<task_result>`: когда задача завершается, персонаж получает собственный ход в разговоре, где задача была запрошена, в ответ на сообщение, которое её начало (вклинивание, если такого сообщения нет). Ход проходит ту же очередь внимания и соблюдает `agents.resultCooldownSeconds` между двумя такими ходами в одном разговоре. Блок содержит id, агента, цель и состояние, текст результата, обрезанный до `agents.resultMaxChars`, источники нумерованным списком и каждый файл как хэндл. Персонаж может ответить или промолчать; задача считается увиденной. Отменённая задача не открывает хода; задача, оставшаяся открытой из-за перезапуска ядра, завершается с `restarted`.
- Хэндлы файлов: `file:<task id>/<name>` указывает на файл, сохранённый задачей. `message.create` принимает его как атрибут `file` и прикрепляет файл из `<agents.<profile>.out>/<task id>/<name>`. Хэндл, не указывающий на файл задач персонажа (или файл приватного чата вне этого чата), отклоняется с `unknown-file`; файл, превышающий ограничения интерфейса, отклоняется с `attachment-too-large`.

## Добавление агента

1. Создайте `agents/<id>/` с `profile.json` (скопируйте один из существующих) и, для воркера, `prompt.md`.
2. Если нужна модельная роль, которой ещё нет, добавьте её в `src/llm/roles.js`.
3. Для воркера: добавьте блок `agents.<id>` в `config.json`, юнит systemd по образцу `deploy/neptunia-agent-web.service` и, чтобы персонаж мог до него достучаться, имя в `TASK_AGENTS` (`src/ops/catalog.js`) и кто может его запрашивать в `src/ops/task.js`.
4. Если ни один существующий класс оболочки не подходит, это изменение кода в `src/agent-runner/profiles.js`, а не ключ профиля.
5. Запустите `tests/agent-runner-profiles.test.js`.
