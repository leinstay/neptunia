# Сообщения и память

Как персонаж обрабатывает сообщения и запоминает людей.

## Конвейер

Сообщение проходит через фильтры гильдии, канала и собственных сообщений. Если персонаж был вызван (@упоминание, ответ или триггер по имени), эвристика игнорирования бросает кость с базовым шансом, с поправкой на пустые пинги, повторные обращения, спам и балл отношения вызвавшего. Базовый шанс: `mention.ignoreChance` для @упоминания и для ответа, в тексте которого персонаж @упомянут; `mention.followUpIgnoreChance` для любого другого ответа персонажу и для продолжения, на которое классификатор ниже ответил `yes`. Для триггера по имени бросается только `mention.nameTriggerChance`. Если бросок не прошёл, сообщение игнорируется; проигнорированные сообщения остаются в транскрипте при построении следующего ответа.

После того как персонаж ответил кому-то, сообщения без обращения в этом канале на протяжении `mention.followUpMinutes` минут отправляются классификатору на роли `classifier.text`, который отвечает `yes`, `overheard` или `no`. `yes` продолжает разговор; `overheard` (разговор о персонаже, а не к нему) запускает отдельный вид хода с `prompts/overheard.md` при включённом `mention.followUpOverheard` (по умолчанию), иначе считается обычным продолжением. Три `no` подряд (`mention.followUpNoStreak`) закрывают окно; `overheard` считается как `yes` для серии. Окна follow-up переживают перезапуск. `features.followUp` выключает классификатор.

Спонтанные ходы запускаются хаотичным таймером или шансом подслушивания на каждое сообщение (`spontaneous.eavesdropChance`). Сообщение, адресованное комнате (а не одному человеку), имеет шанс (`spontaneous.roomQuestionChance`, по умолчанию 0.04) быть подхваченным; классификатор (`prompts/room.md`) предварительно подтверждает, что вопрос открытый; ход сфокусирован на этом сообщении. После `spontaneous.deadAfterMinutes` тишины персонаж может начать тему, даже если последнее сообщение в канале было его собственным; он никогда не вклинивается на своём собственном последнем сообщении. Персонаж не будет говорить спонтанно в канале, молчащем дольше `spontaneous.maxChannelSilenceHours` часов; прямой пинг туда по-прежнему получает ответ.

### Один ответ

Персонаж пишет один ответ за раз на весь сервер (`mention.oneAtATime`). При включённом `mention.pendingSameChannel` (по умолчанию `true`, отсутствующий ключ = включено) прямой пинг (@упоминание, ответ на сообщение персонажа или обращение по имени) в том же канале, пока там идёт ход, откладывается, ответ после завершения текущего хода с паузой `mention.switchDelayMs`, шанс игнорирования бросается в тот момент. Отложенный пинг не получает повторного ответа, если ход, который шёл, уже обработал его в истории. При выключенном переключателе пинг пропускается и появляется только в транскрипте следующего ответа. Прямой пинг в другом канале откладывается так же. Все вызовы ждут в порядке поступления, с одним исключением: отложенный follow-up (`yes` от классификатора, заставший занятый ход) удерживается один на канал, и более новый заменяет предыдущий. При включённом `mention.classifyWhileBusy` (по умолчанию) кандидат на продолжение, пришедший, пока персонаж занят, всё равно отправляется классификатору и может стать отложенным follow-up; при выключенном переключателе кандидат пропускается без вызова классификатора. При подхвате отложенный follow-up проходит те же проверки, что и упоминание, плюс две собственных: окно follow-up канала ещё открыто, и строка не попала в историю хода, который уже ответил там. Затем для него выполняется бросок на игнорирование по `mention.followUpIgnoreChance`. При включённом `mention.pendingOverheard` (по умолчанию) `overheard` от классификатора при занятом ходе тоже ожидает в очереди; персонаж реагирует после завершения текущего хода. Ожидающий follow-up никогда не вытесняется более поздней строкой `overheard`; ожидающая строка `overheard` вытесняется более поздним follow-up, более поздней строкой `overheard` или прямым упоминанием, ответом или обращением по имени. Ожидающая строка `overheard` не учитывается в лимите спама и не сообщается другим ходам как ожидающий вызов в канале. Не более `mention.maxPending` (по умолчанию 6) вызовов удерживается по всем каналам и авторам; сверх лимита вытесняется самый старый (`mention: dropped`, reason `full`). Вызовы истекают через `mention.pendingMinutes` минут. Когда текущий ответ завершён, персонаж переключает канал после короткой паузы (`mention.switchDelayMs`) и отвечает на старейший ожидающий вызов по ситуации в разговоре; обычный шанс игнорирования применяется. Отложенный вызов не получает ответа, пока бот на паузе. Попадания подслушивания, пришедшие, пока персонаж занят, пропускаются. При `mention.oneAtATime: false` каждый канал обрабатывается независимо. Персонаж никогда не пишет там, где у него нет права Send Messages; такие каналы по-прежнему читаются и запоминаются.

Когда приходит вызов от автора, у которого уже есть ожидающие элементы в этом канале (части разделённого сообщения, до которых цепочка ещё не дошла, или ранее поставленные в очередь вызовы), классификатор объединения (`prompts/merge.md` на `classifier.text`, назначение `merge`) решает, относится ли новое сообщение к одному из них. Если да, сообщение вкладывается в этот элемент вместо собственного ожидания; ход элемента видит его через `labels.task.added`. Без файла промпта каждый вызов ставится в очередь отдельно. Логируется как `merge: verdict` или `merge: failed`.

Ход, отвечающий на вызов, перечисляет другие ожидающие вызовы того же автора через `labels.task.queued` (или в составе `{others}` в `labels.task.part` на ходе с разделением), а ожидающие вызовы других участников в канале через `labels.task.queuedOthers`. Вызов, названный таким образом, не отбрасывается как уже виденный в истории хода. Без этих меток действует прежнее правило и вызовы не перечисляются.

При включённом `features.elsewhere` вызов (@упоминание, ответ, имя) в канале только для чтения ожидает окончания разговора, затем персонаж отвечает в первом подходящем канале из `memory.mainChannelIds` со ссылкой на вызов. Обычные правила игнорирования и спама применяются; ожидание не занимает внимание. Более поздний вызов в том же источнике заменяет ожидающий (если он не слабее: имя после тега). Вызов, чьё сообщение удалено (`gone`) или не загрузилось (`fetch-failed`) за время ожидания, отбрасывается. Перезапуск во время ожидания теряет вызов (он остаётся неотвеченным в кольце). Вызовы запоминаются в кольце по каналу (`elsewhere.rememberPings`, по умолчанию 20) на `elsewhere.pingMaxAgeDays` (по умолчанию 7) дней. Персонаж также может спонтанно прокомментировать то, что прочитал в канале только для чтения (логируется как `spontaneous: noticed`); комментарий публикуется в основном канале с `prompts/elsewhere.md` как задача.

### Разделение сообщений

При включённом `features.splitTasks` (по умолчанию) и если прямой вызов (упоминание, ответ, имя, продолжение, ЛС) достаточно длинный и структурированный (`split.minChars`, не менее двух разделителей), классификатор (`prompts/split.md` на `classifier.text`, назначение `split`) определяет, содержит ли он несколько отдельных просьб. Классификатор работает параллельно с подготовкой хода, поэтому одиночный запрос не замедляется. Ответ: слово `one` (одна просьба) или от 2 до `split.maxTasks` строк, каждая начинается с `- ` и содержит одну часть словами автора.

Части становятся цепочкой обычных ходов на одном сообщении. Каждая часть является кандидатом для классификаторов поиска, маршрута и recall своего хода, а запрос персонажа называет часть, на которую отвечает, и остальные (`labels.task.part`). Первая часть отвечает на сообщение, остальные публикуются обычным текстом. Каждая часть имеет свой срок и планку отбрасывания. Часть, на которую персонаж ответил молчанием, ошибкой или отказом, не останавливает следующую. Пауза или прогрев завершают цепочку досрочно (`turn: chain stopped`). Бросок игнорирования, дневной лимит ЛС и отметка в кольце считаются один раз на сообщение. Пока цепочка идёт, ожидающие вызовы продолжают ставиться в очередь; внимание освобождается только в конце.

Настройки: `features.splitTasks`, группа `split` (`minChars`, `maxTasks`, `contextMessages`, `maxOutputTokens`). Без `prompts/split.md` или без `labels.task.part` разделитель выключен. Лог: `split: verdict`, `split: skipped`, `split: failed`, `turn: part`, `turn: chain stopped`.

При включённом `features.pauseNotice` (по умолчанию) вызов, пришедший во время паузы, получает короткий ответ (`labels.limits.paused`). Не чаще одного на канал за `mention.pauseNoticeMinutes` (по умолчанию 10) минут.

### Тайминг

Всё, что выполняется до голосового запроса (история, подписи, классификаторы маршрута и поиска), имеет срок: `pace.prepareMs` (по умолчанию 6 с), расширяемый до `pace.prepareSearchMs` (по умолчанию 12 с), пока классификатор поиска принимает решение и пока выполняется запрошенный им поиск (вердикт «поиск не нужен» снимает удержание немедленно), или до `pace.prepareMediaMs` (по умолчанию 20 с), когда триггер содержит медиа для описателя или видео-модуля; при совпадении обоих расширений побеждает больший лимит. Помощник, не уложившийся в срок, отбрасывается, и ход продолжается без него (логируется как `turn: stage late` или `turn: stage failed`). Готовый ответ должен прийти в пределах `pace.dropAfterMs` (по умолчанию 60 с) от начала хода; после этого ход отбрасывается неопубликованным (логируется как `turn: dropped`). Каждый ход логирует время каждого этапа в `turn: timings`.

Запросы на ролях из `llm.hedge.roles` (по умолчанию: `classifier.text`) хеджируются: вторая попытка стартует через `llm.hedge.afterMs` (по умолчанию 2.5 с) после первой, и первая завершившаяся побеждает. Обе отменяются по `llm.hedge.timeoutMs` (по умолчанию 8 с) от начала. `llm.helperTimeoutMs` (по умолчанию 30 с) ограничивает классификатор маршрута, классификатор поиска и сводку recall по отдельности.

При включённом `pace.typingWhilePreparing` (выключен при поставке) индикатор набора показывается с начала хода, отвечающего на прямой вызов, а не только при набитии готового ответа.

### Запрос

Ход собирает транскрипт канала и соседние каналы, затем строит один запрос к LLM в рамках бюджета токенов. Секции заполняются по приоритету: системный промпт и задача не обрезаются никогда; затем профиль вызвавшего, результат поиска (веб, серверный или оба), серверные привычки и факты о себе, карта каналов, записи лорбука, транскрипт (новейшие сначала), остальные профили и соседние каналы.

При включённом `features.channelRoute` (по умолчанию) классификатор (`prompts/route-channel.md`) определяет, о каком канале идёт речь, из списка до `route.maxChannels` (по умолчанию 40) кандидатов, чтобы подтянуть его в запрос как блок `<channel_view>`. Это работает наряду с явными упоминаниями каналов (`features.channelPull`): классификатор маршрута разрешает косвенные ссылки («тот канал», «канал X»), а реальное упоминание `<#id>` подтягивается напрямую.

Модель видит карту каналов сервера (назначение, темы, тон, уровень активности) с текущим каналом, отмеченным специально. Каждая запись канала также содержит факты, которые ведёт код: количество сообщений, первое и последнее сообщение, гистограмму активности за 30 дней и самых активных авторов (`memory.channelWritersStored`, с затуханием по `memory.channelWritersHalfLifeDays`). Прогрев заполняет их из истории канала, и живой трафик поддерживает их актуальность. Когда заметкам канала не менее `memory.notesStaleDays` (по умолчанию 7) дней, в батче не менее `memory.notesBatchLines` (по умолчанию 8) строк из этого канала, с момента последнего изменения или проверки заметок подсчитано не менее `memory.notesMinMessages` (по умолчанию 30) сообщений и предыдущая пометка отправлена более `memory.notesRetryHours` (по умолчанию 24) часов назад, анализатор получает пометку устаревания и отвечает через `note_reviews` (`updated`, `confirmed` или `insufficient_evidence`). Проверкой считается только подтверждённый результат или реальное изменение текста; при недостаточных свидетельствах или отсутствующем ответе таймер продолжает идти.

Модель отвечает тегами `<think>` (скрытое планирование), `<msg>` (от 1 до 3 сообщений в чат; `reply="#87"` отвечает на строку транскрипта), `<react>` (одна эмодзи-реакция) или `<skip/>` (молчание). После разбора текст набирается с человеческой скоростью, а `@nick` в выводе становится реальным упоминанием. Участники, выбравшие `/nep pings off`, не получают уведомлений от сообщений персонажа: ответы приходят без пинга, а @упоминания отображаются, но не уведомляют. Каждое сообщение обрезается до лимита Discord в 2000 символов. Сообщение, не отправившееся, логируется (`turn: send failed`) и прерывает публикацию этого хода.

## Недавние заметки

При включённом `features.recent` (по умолчанию) блок `<recent>` показывает, что произошло на сервере за последние `memory.recentHours` (по умолчанию 72) часов: короткие датированные строки, которые пишет анализатор, и недавние эпизоды участников, к которым обращается ход. Строка появляется только из канала хода или из канала, доступного для чтения всем здесь присутствующим; в приватном чате только из каналов, доступных каждому участнику сервера, без эпизодов. Элементы о людях, к которым обращается ход, ранжируются первыми. Блок ограничен `context.caps.recent` (по умолчанию 1200) токенов.

Анализатор записывает не более `memory.maxNewRecent` (по умолчанию 3) строк за батч, каждая до `memory.recentChars` (по умолчанию 160) символов. Строки хранятся в `data/guilds/<id>/recent.json` (до `memory.maxRecentStored`, по умолчанию 150) и устаревают по `memory.recentHours`. `/nep memory recent` показывает текущие строки.

## Анализатор

Анализатор памяти запускается как отдельный вызов LLM, когда накопится достаточно сообщений (`memory.batchMessages`, `memory.minBatchMessages`, `memory.maxBatchAgeMinutes`). Он получает карточку персонажа и оценивает каждого человека глазами персонажа, возвращая дельты отношения, изменения профилей, наблюдения по каналам и серверные заметки.

Когда батч слишком велик для лимита токенов, анализируются только помещающиеся строки с начала, а остальные откладываются на следующий батч (лог показывает `consumed`, `shown` и `deferred`). Тихий приватный буфер (нет новых сообщений `memory.privateMaxAgeMinutes`, по умолчанию 360 минут) анализируется, даже если не набрал `minBatchMessages`. Списки шуток и фактов о себе освобождают место для новых записей, вытесняя самую давнюю, когда список полон. Лор вытесняет самую давнюю запись при достижении `lore.maxEntries`.

Неудачный батч (обрезанный вывод, неразбираемый JSON, превышение лимита токенов) уменьшает размер батча вдвое для следующей попытки. Когда батч уже на минимуме (20 сообщений) и всё равно не проходит, вместо немедленного повтора выставляется пауза на 15 минут (логируется как `memory: update failed ... backing off` с `atFloor: true` и `backoffMs`). Буфер сохраняется в обоих случаях.

### Профили

Профили обновляются инкрементально: анализатор возвращает только то, что изменилось, и сохранённые факты никогда не пересказываются. Каждый профиль содержит:

- **Характер и стиль**: прозаические абзацы, написанные целиком промптом профиля (`profile.md`) при прогреве и обновляемые из недавних сообщений кодом (по расписанию на основе счётчиков) или когда анализатор отмечает пробел или противоречие. Потоковый анализатор никогда не редактирует их напрямую; `character` и `style` из потокового батча отбрасываются.
- **Интересы**: атомарные элементы с темой и заметкой. Ранжируются по частоте и новизне с весом, затухающим со временем (`memory.interestHalfLifeDays`). На каждого человека хранится больше элементов, чем показывается (`memory.maxInterestsStored` против `memory.maxInterests`), поэтому новичок может набирать вес в невидимом хвосте. Интересы, не встречавшиеся `memory.interestStaleDays` дней, показываются персонажу как устаревшие.
- **Детали**: атомарные элементы (факт, черта, контекст). Те же механики ранжирования и подтверждения, что у интересов, со своим периодом полураспада (`memory.detailHalfLifeDays`).
- **Псевдонимы**: как люди в чате реально называют участника. Персонаж узнаёт участника, упомянутого по имени или псевдониму, даже если тот не в разговоре.
- **Отношения**: как персонаж относится к этому человеку, написано голосом персонажа.
- **Отношение**: балл от -100 до 100 (`features.relationships`). Анализатор возвращает небольшую дельту, никогда не абсолютный балл. Балл не показывается в чате; он проявляется в том, сколько усилий персонаж вкладывает. Баллы ежедневно дрейфуют к нулю при установленном `relationships.decayPerDay`, тем быстрее, чем дальше от нуля. Текст relationship помечается для переписывания при устаревании: смена полосы (с гистерезисом `relationships.bandHysteresis`), дрейф на `relationships.rewriteOnDrift` пунктов с момента записи или `relationships.rewriteAfterMoves` движений отношения. Текст ограничен `relationships.textChars` (по умолчанию 600).

Портрет характера и манеры речи участника строится по каналам из `memory.mainChannelIds`; когда список пуст, все каналы считаются основными. `memory.mainChannelIds` также определяет канал-назначение для ответов на вызовы из каналов только для чтения (`features.elsewhere`). Сохранённая память ссылается на участников по id, и текущее имя подставляется при использовании, поэтому переименования не ломают заметки.

### Подтверждение

Интересы и детали используют общий механизм подтверждения. Новый элемент начинает с веса 1 (или 0, когда анализатор помечает его `"sure": false`). Наблюдение на отдельном случае (с промежутком не менее `memory.confirmGapHours`) увеличивает вес на 1. Элемент считается подтверждённым при весе ≥ `memory.confirmAfter`; до этого персонаж видит его с пометкой «(не подтверждено)». Псевдонимы используют те же механики ранжирования и наблюдений, но механизм `"sure": false` и пометка неподтверждённости к ним не применяются. Ранг всех трёх: `log2(weight + 0.5) + lastSeen / halfLife`, поэтому частое И недавнее наверху.

## Эпизоды

Эпизоды это моменты, которые персонаж помнит об отдельных людях: оскорбление, доброта, обещание, пари, общая шутка, просьба что-то сделать или никогда не делать. Анализатор добавляет их в профиль человека с датой, кратким описанием, иногда дословными словами и весом от 1 до 5. Самые тяжёлые живут дольше всего; когда профиль достигает `memory.maxEpisodes`, сначала вытесняются самые лёгкие, затем самые старые. Показываются только эпизоды вызвавшего, внутри блока `<people>`.

## Лорбук

Лорбук хранит серверные знания, которые переживают любой разговор: события, повторяющихся персонажей, длительные истории, конфликты, традиции. Каждая запись содержит заголовок, набор ключевых слов и короткий текст (`lore.textChars`). Код сканирует последние `lore.scanMessages` сообщений на совпадение ключей и включает до `lore.maxMatches` записей в блок `<lore>`; записи с пометкой `always` появляются всегда. Записей могут быть сотни при ничтожных затратах, потому что показываются только подходящие.

Анализатор добавляет и обновляет записи лорбука, но никогда не трогает записи, добавленные владельцем через команды `/nep lore`. Данные лорбука хранятся в `data/guilds/<id>/lore.json`.

Дневник хранит историю постов в `data/guilds/<id>/diary.json` (однострочные краткие содержания, от старых к новым, с лимитом `diary.historyPosts`). См. [Дневник](diary.md).

Анализатор также записывает то, чему люди научили персонажа напрямую (слова и выражения, факты о сервере, просьбы о поведении) как серверные уроки, которые всегда присутствуют в промпте.

## Приватный слой

Когда `features.privateMessages` включён, участники, прошедшие шлюз (членство в сервере, сохранённый профиль, публичное отношение не ниже `private.minAffinity`, сегодняшний счётчик ответов в пределах лимита), могут писать персонажу в личные сообщения Discord. Персонаж остаётся тем же с той же публичной памятью; сказанное в ЛС хранится в приватном слое для каждого участника. Когда `features.privateLikeServer` включён (по умолчанию), ЛС работает как серверный канал: классификатор маршрута, подтягивание каналов, серверный поиск и эпизоды упоминаемых участников доступны с ограничением по каналам, видимым собеседнику.

Просматривать приватный слой участника (`/nep memory private show`) могут только владельцы бота; эту команду нельзя выдать другим пользователям.

Приватный файл `data/guilds/<guildId>/private/<userId>.json` хранит собственные `relationship`, `interests`, `details`, `episodes`, `affinity` (начальный балл 0), дневной счётчик ответов и буфер наблюдений. Никогда не показывается другим разговорам, никогда не записывается серверным батчем, никогда не смешивается с публичным профилем на диске. Публичный профиль не меняется от ЛС.

В ЛС персонаж видит объединение публичных и приватных данных: интересы объединяются по теме (приватная заметка побеждает), детали конкатенируются, эпизоды сортируются по дате, абзацы `relationship` соединяются. Эффективное отношение: `clamp(публичный + приватный, -100, 100)`. На сервере персонаж видит только публичный балл.

Приватный анализатор (`analyzePrivate`) запускает тот же промпт `memory.md` с блоком `<private>`. Из ответа применяется только `users[<partnerId>]` через методы приватного хранилища; `portrait`, `aliases`, `guild`, `channels`, `lore`, `self` и другие id отбрасываются.

`/nep memory forget <user>` удаляет и публичный профиль, и приватный файл. `/nep memory wipe` удаляет всю директорию `private/` для сервера. `/nep memory private forget <user>` удаляет только приватный файл; публичный профиль сохраняется.

## Когда заметка стала бы слишком длинной

У каждого прозаического поля памяти (характер, стиль или текст отношения участника; назначение, темы или тон канала; серверные паттерны и зачины; текст записи лорбука) есть лимит символов. Когда модель пишет замену, превышающую лимит, новый текст не сохраняется: старый текст остаётся как был. Код никогда не укорачивает перезапись модели.

Голосовая модель, обновление портрета и обновление заметок получают одну повторную попытку. При повторе модель получает свой же ответ и пометку с точным числом символов и лимитом по каждому полю, и её просят уложить то же содержание за счёт удаления повторов. Если укороченная версия помещается, она сохраняется как обычно. Если снова не помещается, старый текст остаётся.

Потоковый анализатор не повторяет. Если поле в батче переполняется, остальные изменения батча применяются; пропускается только это поле.

Единственное исключение: самая первая запись пустого поля: поскольку старого текста для сохранения нет, ответ модели принимается и обрезается по лимиту на границе предложения.

### Старые версии

При включённом `features.versions` (по умолчанию вкл.) каждый раз, когда текст прозаического поля заменяется, предыдущий текст сохраняется в `data/guilds/<id>/versions/`. Каждая запись хранит дату, кто её записал (анализатор, голосовая модель, обновление портрета, обновление заметок, прогрев или владелец), предыдущий текст и предложенческое сравнение.

Сравнение предложений содержит три числа: `kept` (предложения, присутствующие и в старом, и в новом тексте), `removed` (предложения из старого текста, отсутствующие в новом) и `added` (предложения из нового текста, отсутствующие в старом). Когда `kept` равно 0, а в старом тексте было несколько предложений, модель заменила текст целиком вместо слияния. Именно такие перезаписи история версий призвана ловить.

Не более `memory.versionsKept` (по умолчанию 20) записей хранится на поле. `/nep memory forget` удаляет файл версий участника. `/nep memory wipe` удаляет все файлы версий сервера.

## Команды

Полный список команд: [Команды](owner-commands.md). Наиболее важные для памяти:

| Команда | Что делает |
|---|---|
| `/nep memory recent` | Показать текущие недавние заметки |
| `/nep memory show <user>` | Краткая сводка или конкретная секция сохранённого профиля |
| `/nep memory channel` | Сохранённые заметки канала и факты, которые ведёт код |
| `/nep memory server` | Серверные привычки, внутренние шутки, факты о себе |
| `/nep memory refresh <user>` | Принудительно обновить портрет участника |
| `/nep memory forget <user>` | Удалить сохранённый профиль и приватную память |
| `/nep memory affinity <user>` | Показать или установить отношение (-100..100) |
| `/nep memory wipe` | Стереть всю память анализатора для этого сервера, включая приватные файлы |
| `/nep memory private show <user>` | Показать приватную память участника |
| `/nep memory private forget <user>` | Удалить только приватный файл; публичный профиль сохраняется |
| `/nep lore add` | Добавить или перезаписать запись лорбука |
| `/nep pause` / `/nep resume` | Остановить активность и сбросить память на диск для безопасного ручного редактирования |
