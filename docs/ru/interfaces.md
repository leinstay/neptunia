# Интерфейсы: протокол между ядром и адаптером

У движка две стороны: ядро (персонаж, его память, его решения о том, когда и как говорить) и интерфейсы (чат-платформы, на которых он живёт). Адаптер интерфейса преобразует события платформы во входящие события для ядра и выполняет действия, которые ядро отправляет обратно. Каждое действие получает результат. Контракт между двумя сторонами живёт в `packages/protocol/` (`@neptunia/protocol`): простые объекты, без этапа сборки, без зависимостей, без платформенных типов на обеих сторонах.

| Файл | Содержимое |
|---|---|
| `packages/protocol/events.js` | виды входящих событий и их формы |
| `packages/protocol/actions.js` | имена действий, форма результата и хелперы порта (`ok`, `notOk`, `mentionsOf`, отказы, `declaredHooks`) |
| `packages/protocol/validate.js` | `validateEvent(event)` и `validateAction(action)` |

Движок импортирует пакет через `src/protocol.js` (единственное место для переключения на голый спецификатор `@neptunia/protocol`, когда пакет станет npm workspace); `src/interface/port.js` реэкспортирует исходящую часть. Адаптер Discord — это пакет `interfaces/discord/` (`@neptunia/interface-discord`, доступный через `src/interface/discord.js`): `port.js` (действия) с конструкторами событий в `collect.js` (`toEvent`, `reactionEvent`); адаптер в памяти для тестов — `src/interface/fake.js`.

Ядро общается с Discord только через то, что даёт ему корень композиции. Помимо порта, `createDiscordInterface({ client })` возвращает замороженный объект возможностей: функции, которые ядро запрашивает у Discord по имени (может ли персонаж читать, отправлять, прикреплять или реагировать в канале, история канала, другой канал для показа, поиск по сообщениям и участникам сервера, сообщение как событие протокола и обратно). `src/index.js` собирает его один раз и передаёт как `discord` каждому модулю: фабрике через опции, операции через окружение (`env.discord`), чистому хелперу как параметр. Ни один другой файл в `src/` не импортирует интерфейс Discord, поэтому тест или инструмент подставляет те же функции или их имитации.

## Правила

- Id — непрозрачные строки. Разговор, сообщение, участник, эмодзи или id события — это строка, которую умеет читать только адаптер, её создавший. Ядро сравнивает id, но не разбирает их. Ссылки в действиях привязаны к пространству имён адаптера (`iface`: `discord`, `fake`).
- Платформенные объекты не пересекают границу. Событие или действие — простой сериализуемый объект. Адаптер Discord, пока он ещё живёт внутри движка, также несёт `raw` (и `rawPrevious` для редактирования) на своих событиях: дескрипторы объектов discord.js, доступные только на стороне Discord, никогда в `src/behavior/`, игнорируемые валидацией и убираемые после переезда адаптера в отдельный пакет.
- Упоминание — это обращение. Сообщение, которое упоминает персонажа или является ответом на её сообщение, — это одно `message.received`, чьё `addressing` об этом сообщает, а не отдельное событие.
- Приватный чат — это вид разговора. Личное сообщение — это `message.received` в разговоре вида `dm`, а не отдельный вид события.
- Валидация не бросает исключений. И `validateEvent`, и `validateAction` возвращают `{ ok: true }` или `{ ok: false, reason }`, где `reason` указывает поле и проблему (`message.at:type`, `kind:unknown`, `conversation.id:required`). Ядро отбрасывает невалидное входящее событие с одной строкой предупреждения, `interface: invalid event`, с указанием вида и причины, но без содержимого. Фейковый адаптер отклоняет невалидное действие как `failed` с кодом `invalid-action`.
- Валидация проверяет только формы. Проверяются виды, обязательные ключи, строковые id, конечные числа и флаги. Принадлежит ли ссылка этому интерфейсу, помещается ли контент в лимиты и кто может выполнять команду — это ответственность адаптера и ядра.

## Входящие события

Каждое событие содержит `kind`, `iface` (пространство имён адаптера), `at` (миллисекунды с эпохи), `id` (непрозрачный id события для дедупликации) и, для всего, что происходит в разговоре, объект `conversation`:

| Поле | Содержимое |
|---|---|
| `id` | id разговора |
| `kind` | `channel`, `dm` или `thread` |
| `guildId` | сообщество; null или отсутствует для приватного чата |
| `name`, `topic`, `category` | что видят участники; null или отсутствует, когда неизвестно |

Пять видов событий:

| Вид | Отправитель | Содержимое |
|---|---|---|
| `message.received` | адаптер | `message`, `addressing`; `edit: true` для редактирования (тот же id сообщения), `deleted: true` для удаления (только `message.id`), `edit: true, partial: true` для редактирования, которое адаптер не смог прочитать целиком (только `message.id`; ядро запрашивает остальное у адаптера) |
| `reaction.changed` | адаптер | `messageId`, `emoji` (`{ name, id? }`: `name` — сам unicode-эмодзи или имя серверного эмодзи, `id` — id серверного эмодзи; одно из двух обязательно), `userId`, `added` (true при постановке, false при снятии) |
| `command.requested` | адаптер | `name` (`group.sub` или `sub`), `args` (объект), `requester` (`{ id, name, roles, owner }`: `name` может быть null, `roles` — id ролей, `owner` — указан ли вызывающий среди настроенных владельцев; для информации: ядро проверяет права само), `replyRef` (непрозрачный токен; ответ возвращается как действие `command.result` с ним) |
| `scheduler.tick` | ядро | только `at`: собственные часы ядра. Адаптер это событие не отправляет; `iface`, `id` и `conversation` не обязательны |
| `task.completed` | ядро | `taskId`, `status`, `result` (как определяет `src/errands`); `iface`, `id` и `conversation` не обязательны |

`message`:

| Поле | Содержимое |
|---|---|
| `id` | id сообщения |
| `author` | `{ id, name, self, bot }`: `name` — отображаемое имя автора или null; `self` — true для собственных сообщений персонажа; `bot` — для другого автоматизированного аккаунта |
| `content` | текст как его видят люди (упоминания записаны именами) |
| `at` | когда написано |
| `replyToId` | сообщение, на которое это ответ, или null (пересланное ни на что не отвечает) |
| `replyPingUserId` | автор сообщения, на которое это ответ, когда уведомление пришло только через ответ, или null |
| `forwardedFrom` | имя разговора, из которого пришла пересылка, или null |
| `attachments`, `links`, `forwarded`, `stickers`, `emojis`, `reactions` | массивы, в формах, которые задаёт `interfaces/discord/collect.js#normalizeMessage` |

`addressing`:

| Поле | Содержимое |
|---|---|
| `mentioned` | персонаж среди упомянутых |
| `replyToSelf` | сообщение является ответом на одно из сообщений персонажа, насколько известно адаптеру без повторного запроса к платформе (ядро может дополнительно проверить) |
| `mentionedUserIds` | все упомянутые в сообщении участники |
| `mentionedConversationIds` | все упомянутые в сообщении разговоры |

## Действия

Каждое действие — простой объект с именем `action`. Первые шесть — возможности порта, имена, которые адаптер перечисляет в `capabilities().operations`:

| Действие | Поля |
|---|---|
| `message.send` | `conversation` (`{ iface, conversationId }`), `content` |
| `message.edit` | `message` (`{ iface, conversationId, messageId }`), `content` |
| `message.delete` | `message` |
| `message.react.add` | `message`, `emoji` (строка) |
| `message.react.remove` | `message`, `emoji` |
| `conversation.typing` | `conversation` |
| `command.result` | `replyRef` (из `command.requested`), `text`, необязательные `files`, необязательный `ephemeral` (видит только вызвавший) |

`content` — это `{ text?, attachments?, replyTo?, mentions? }`: `attachments` — `{ name, data?, url?, contentType? }`, `replyTo` — ссылка на сообщение того же интерфейса, `mentions` — `{ users, repliedUser }`, участники, которых сообщение может уведомить. Отсутствующие mentions означают, что никто не уведомляется. Null-часть считается отсутствующей.

## Результаты

Каждое действие получает результат; адаптер никогда не бросает исключений.

| Поле | Содержимое |
|---|---|
| `status` | `ok`; `failed` (действие точно не произведено); `unknown` (действие могло быть произведено, поэтому слепой повтор недопустим); `unsupported` (этот интерфейс не может выполнить действие); `forbidden` (этот интерфейс не имеет права, например при попытке удалить чужое сообщение) |
| `ref` | сообщение в его текущем виде (для отправки — новое сообщение), если есть |
| `at` | когда интерфейс пометил результат, если сообщает |
| `error` | `{ code, retryable }`, когда статус не `ok`: `code` — строка в kebab-case (`empty-content`, `text-too-long`, `invalid-attachment`, `attachment-too-large`, `foreign-reference`, `invalid-reference`, `not-own-message`, `unknown-message`, `invalid-action`, `timeout`) или `http-<status>`, и `retryable` — может ли повторная попытка позже помочь. Адаптер может добавить `cause` для своих логов; оно не попадает к модели |

Адаптер редактирует и удаляет только собственные сообщения персонажа (возвращая `forbidden` в противном случае) и отклоняет ссылку другого интерфейса как `foreign-reference`.

## Ещё не реализовано

Адаптер Discord — отдельный пакет (`interfaces/discord/`), но пока работает внутри процесса движка и переедет в отдельный на следующем этапе. До тех пор пайплайн сообщений читает нормализованное сообщение, построенное из события, команды владельца отвечаются прямым ответом, а не действием `command.result`, а `scheduler.tick` и `task.completed` ядра — прямые вызовы, а не события через единый диспетчер.
