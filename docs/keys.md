# Keys and models

The persona's model credentials live in `data/keys.json`, and that file holds secrets alone: the core keys, the extra keys, the service credentials and the `management` key. Which part of Neptunia runs on which key, harness, model and effort lives in the private settings file `data/config/config.json`, under `llm.boundKeys`, `models.agents` and `models.harness` (see [configuration](configuration.md#modelsagents)). `src/subharness/routing.ts` reads and writes those settings, and no write of the engine leaves `roles`, `subharness` or `simulation` in `keys.json`. Interface and skill credentials live beside the module they belong to. The CLI dialogs create and change them, and no secret value is printed.

## Named keys

`/keys add <name>` asks the value of an OpenRouter key through the chat's masked question, checks it with the free read of `/auth/key` and saves it under that name. The first key of an empty `keys.json` asks the models of `core`, `memory`, `analyzer` and `embedding` too and checks each on the new key before anything is saved. A role runs on a key once a route of its [chain](#chains-of-routes) names it, so the answer names `/model set <role> <name>/<model>`. `/keys list` shows every key by name and last four characters with the roles whose chains name it. `/keys check <role>` sends one minimal request on the role's route in force, and `/keys check <name>` reads the key's record for free.

`/keys remove <name>` takes a key out of `keys.json`. A chain that named it keeps that route, written to `models.routes` first, and the route is skipped until a key of that name comes back. When her core is left with no route it can take, a harness or a key `keys.json` holds, she is paused with `no-core-route`, and the `/keys add` that gives the core a route again lifts that pause and no other.

[`checkRole`](../src/keys/check.ts) sends one minimal request for the role on the role's key. Chat roles get a short completion, `embedding` a short embedding, and `speech` a synthesis of two characters on the speech endpoint with `speech.voice`. A failed check means the provider or the network said no. `drawing` has no probe, because one request bills a whole picture, so `/keys check drawing` answers `unsupported` and sends nothing, and `/model set drawing` saves the model unverified. A role that is off answers `not_configured`. Neither answer says anything about the key.

A role that runs through a harness needs no API key, and a missing key does not stop it. `/keys check core` on such a core answers that the role needs no key. The same holds for `memory`: the role health (`roleKeyCheck` in `src/llm/role-health.ts`) counts a role whose route in force is a harness as served, and the `harnessOf` dependency of `createKeysCommands` reads it from the chain. The memory session's sweep and its description review take the writer's path at the moment they run (`refusalOf` and `memoryKeyState` in `src/memory/db/session.ts`, `reviewRefusal` in `src/memory/db/describe.ts`, the `sessionPath` dependency of the memory service), so a writer on a harness runs with no memory key. Every request of the role `memory` goes through `memoryWriterClient` in `src/subharness/memory-writer.ts`: the sweep's, the review's draft and check, and the description join of a `/memory bind` merge. On a harness path each one is a run of that backend, and on the direct path each one spends the bound memory key or is refused with `ROLE_KEY_MISSING`. A role on the API with no key is reported missing as before.

`/keys check memory` checks the path the memory writer runs on, which `src/subharness/memory-path.ts` reads from `models.harness.memory`. On `direct-api` it is the request on the memory key, and the answer ends with `(direct path)`. While the writer runs through `claude-harness` or `codex-harness`, it is the probe of `src/subharness/memory-probe.ts` through that backend, the answer names the backend and model, and no request goes out on the OpenRouter key, so the check needs no core key.

The base chat roles, the memory writer and the delegated agents are distinct routes. `/model set core` and `/keys check core` record their check for [chat readiness](setup.md#chat-readiness), so a launch sends no model request of its own. A subscription login for an agent backend does not replace the OpenRouter keys used by the core. See [setup](setup.md#subharness-backends) for those logins.

## Chains of routes

Every request of a model role (`core`, `memory`, `analyzer`, `vision`, `video`, `embedding`, `speech`, `drawing` and `search`) walks the role's chain of routes. A route is a request on a named key of `keys.json` with a model, written `<key>/<model>[:<effort>]`, or one run of a subscription CLI with a model, written `harness:<claude|codex>/<model>[:<effort>]`. `src/llm/route-text.ts` reads both forms, and refuses a harness route on a role other than `core` and `memory` with `route-unsupported`, so `embedding` runs on OpenRouter alone. Every role takes an effort. A route that names none takes the effort `llm.routeEffort` gives its role. It ships with `core` at `lowest`, the least each route offers: an API route sends no `reasoning`, and a harness route runs at `low`.

`routesOf` in `src/llm/route-chain.ts` reads the chain from `models.routes.<role>` of `config.json`. A role with no entry there runs on the routes its other settings give it: its harness record in `models.harness`, then one route per core key, or the extra key `llm.boundKeys` binds it to, with the model of `models.base` (`web.quickSearch.model` for `search`) and the effort of `llm.reasoningByRole`. The core's harness route is followed by its API routes only while `llm.subscription.fallback` is `true`, and the memory writer's harness route has none behind it.

`createChainClient` in `src/llm/chain-client.ts` sends a request on the route in force. An API route that answers HTTP 401, HTTP 402, or a 429 whose body names credits or balance, and a harness route that fails with a subscription code such as `subscription-exhausted` or `subscription-login`, hand the same request to the next route. A route whose key `keys.json` lacks is skipped with no request. Any other failure, such as a 400 or a refusal of a rail, fails the request where it is. A request counts once against `llm.maxRequestsPerDay` and tries each route at most once. A chain of one route fails with that route's own error, and a longer chain whose every route was unavailable fails with `routes-exhausted`, which keeps the role down until 00:00 UTC (`src/llm/role-health.ts`).

After a switch the role stays on the later route for `llm.routeRetryMinutes` (default `30`), and its next request after that tries the first route again. When the last route fails, the chain wraps to the first unless the first failed within the last minute. `llm: route switched` logs the role, both routes in their text form and the code, never a key value. The embedder, the speech synthesis and the pictures read the key of their role's first usable API route at each request, and a failure of theirs that makes that route unavailable moves the role to its next route for the next request (`reportingFailures`). The probes, the status header, the memory session and the key commands read a role's key and route from its chain too (`src/llm/core-routes.ts`).

## Setting a chain

`/model show` prints the chain of every model role in the text form, its routes joined by `, then `. `/model set <role> <route>` replaces the role's chain with one route, `/model add <role> <route>` appends a fallback to its end, and `/model remove <role> <n>` drops the route at position `n`, counted from 1. Set and add check the route first: a route on a key with one request of `checkRole` on that key and model, a route on a harness with one reply through it (`checkedRoute` in `src/subharness/selection.ts`). A refused check saves nothing. `src/keys/commands.ts` writes the chain to `models.routes.<role>`, which the next request reads. A route on a key `keys.json` lacks is refused with `key-unknown`, a route already in the chain with `route-duplicate`, and a fallback of `embedding` with another model with `route-model-mismatch`, since vectors of two models do not compare. Removing the last route of `core`, `memory`, `analyzer` or `embedding` is refused with `route-required`, and removing the last route of an optional role turns it off. `--via`, `--effort` and `--provider` are refused for a model role with `flag-retired`: the route's text names the harness and the effort, and `/routes set` pins a model's providers.

## Model sources

The owner reads and types four route names: `direct-api` for OpenRouter, and `claude-harness`, `codex-harness` and `opencode-harness` for the three CLIs. `src/subharness/route-names.ts` maps them at the edge, to render a route and to read `--via`. `keys.json`, the folders under `data/subharness/`, the binaries and the log fields keep the stored word (`claude`, `codex`, `opencode`). A `--via` value that is no route name, including the stored words, is refused with `unknown-backend`, and the answer names the four. `--via direct-api` on `core` or `memory` returns the role to the API as the same command with no `--via` does, and an agent refuses it with `backend-unsupported`.

A source is OpenRouter or a subharness backend that is installed and logged in. `/model set <agent> <model> --via <route> [--effort <effort>]` serves every agent role (`scout`, `server`, `dev`, `watcher`, `thinker`), and it writes the source, the model and the effort in one change. `/model set <agent> <model>` with no `--via` keeps the source in force. An effort that is not given stays while the source stays and goes with a source that changes, because no reply checked it there. `--provider <slug>` with `--via opencode-harness` pins an agent to one OpenRouter provider, see [errands](errands.md#the-provider-of-an-opencode-route).

`checkedSelection` in `src/subharness/selection.ts` checks the source first, then asks one reply from that model, and saves only when the source can still run and nobody changed the selection during the reply. A refusal saves nothing and answers one of these codes.

| Code | Meaning |
|---|---|
| `not-installed` | The backend is not installed; no request was sent |
| `not-logged-in` | The backend is installed with no login; no request was sent |
| `model-rejected` | The reply did not come; the answer carries the backend's last line |
| `role-unsupported` | The role has no subharness path, as `speech` and `drawing`; no request was sent |
| `selection-changed` | Another selection of that role was made during the reply |
| `source-changed` | The source logged out during the reply |

A level past `low`, `medium` and `high` needs proof from the installed binary. `effortLevelsOfHelp` in `src/subharness/place.ts` reads the list a `--effort` flag prints in its `--help`, as `(low, medium, high, xhigh, max)`, and `setAgentModel` and `setMemoryPath` store `xhigh` or `max` only from a backend that lists it. `--effort default` on an agent drops the stored level, so it runs at its model's default. The direct path takes `low`, `medium` and `high` alone.

`modelChoices` in `src/subharness/model-sources.ts` lists the choices of a role by source, so one model name from two sources stays two choices. It labels the fixed names of `codex` and `claude` as suggestions, reports a missing install, a missing login and a provider's refusal as separate notices, and sends no model request. `memory` is never offered `opencode`, which takes no system prompt of its own.

The memory writer differs by path, and `memoryCapabilities` in `src/subharness/memory-writer.ts` says how. On `claude-harness` the session's system text replaces the CLI's own and the run has no tools, and its usage splits into prompt, cached and completion tokens. On `codex-harness` the system text comes first on its stdin, its own instructions stay in force, its sandbox is read-only and its usage is one total, counted as input. `memoryDb.session.maxOutputTokens` reaches `claude` as `CLAUDE_CODE_MAX_OUTPUT_TOKENS`, which it enforces. `codex` has no such control. That gap shows in `/subharness status` and in a passing memory probe on `codex`, and nothing trims her answer instead. An envelope with `stop_reason` `refusal` or `max_tokens` is a failed run (`model-refused`, `output-truncated`), which leaves the session's cursor where it was. The memory probe fails with `not-logged-in` and no model run when the vendor's own status says so, she sleeps with `memory-down`, and no other source answers in its place. `session_runs.model` holds `<backend>:<model>` for a run on a subharness, successful or not, and the role's model on the direct path.

`models.agents.via` holds each agent's source, `models.agents.model`, `models.agents.effort`, `models.agents.provider` and `models.agents.mode` its model, effort, pinned provider and mode, and `models.harness.memory` the memory writer's path. An empty map or a null record is left out of the file.

## Her core on a subscription

`/model set core harness:claude/<model>` or `harness:codex/<model>`, with an optional `:<level>`, moves her turns from the OpenRouter API to the subscription that CLI is logged into, after one reply on that model through it, and `/model add core <key>/<model>` puts an API route behind it. `opencode` is refused with `route-unsupported`, because `opencode run` takes no system prompt of its own. `/subharness status` ends with a `core` row, `direct-api` or `via <harness> <model>` with its effort. The row is marked `unavailable` while its backend cannot run, and `no thinking control` on Codex.

`createSubscriptionClient` in `src/subharness/subscription-client.ts` sits in front of the API client and takes the requests of the role `core` alone. The analyzer, vision, memory and every other role go to the API client unchanged. The step loop calls it once per step, as it calls the API. A turn's first step starts one `claude -p` or `codex exec` from the persona's own install in `data/subharness/<backend>/`, with her system text in place of the CLI's prompt and her user text on stdin. The later steps of the turn continue that process. Claude runs with `--system-prompt`, `--tools ""`, `--setting-sources ""`, `--no-session-persistence`, `--strict-mcp-config` and `--output-format stream-json`, and its native thinking is off through `MAX_THINKING_TOKENS=0`. Codex reads her system text from the file `-c model_instructions_file` names, runs `--ephemeral` with the user config ignored, and has its shell, patch, image and web tools turned off. The child gets the plain host variables and the backend's home, never a key of the core.

Her tools reach the CLI as the MCP server `nep`. The CLI starts `bin/neptunia-mcp.ts` with the core socket and a file that holds a token for this turn alone. The server lists her tool definitions with their names bare, and Claude shows them to the model as `mcp__nep__<name>`. Each call travels over the core socket to the tool bridge of `src/subharness/tool-bridge.ts` and waits there while the step loop runs it through the gateway and the executors, as on the API. The next step hands the result back. A token that is unknown, or whose turn has ended, is refused with `turn-unknown`. A run that ended on tool calls and gets no next step within `llm.subscription.holdMs`, 60000 milliseconds by default, is killed.

Each step passes the token cap and the daily request cap before anything starts, records its tokens in `/usage` at no cost and writes one `model_requests` row whose backend is `claude` or `codex`. A failed step rejects with one of these codes, and her turn's `reason` carries it:

| Code | When |
|---|---|
| `not-installed` | The backend's binary is not in its place, and nothing starts |
| `subscription-exhausted` | The window is spent: Claude rejected the request in a `rate_limit_event` or ended with status 429, or Codex named a usage limit |
| `subscription-login` | The CLI is not logged in |
| `subscription-failed` | Any other failed run, or a CLI that ended before its answer |
| `subscription-timeout` | No event came within the request's timeout, or the request was aborted |
| `subscription-lost` | A later step names tool calls that no open run holds |

`llm.subscription.fallback` at `true` puts the core's API routes behind its harness route in its chain, so a failed step goes to the API with the same messages, when `keys.json` holds a key for the role, a core key or the extra key `llm.boundKeys` binds to it. With no key the step fails as if fallback were off, and no API request is made. A refusal of either rail never goes there. `llm.subscription.thinking` at `true` leaves Claude's native thinking on. Both are `false` by default. Codex has no switch that turns a reasoning model's thinking off.

The paid scripts under `scripts/` run on production's setup. `scriptRouting` in `scripts/lib/script-routes.ts` builds a script's clients with the core's builders: the chain client over each role's chain, the subscription client and `memoryWriterClient`, each read at the moment of a request. A flag `--<role> <route>` replaces that role's whole chain for the run and writes nothing to `config.json`. `<key>/<model>[:<effort>]` sends the role on that key of `keys.json` alone, with that model, and an effort becomes the request's `reasoning`. `harness:<claude|codex>/<model>[:<effort>]` sends `core` or `memory` through that harness. Before any request the script refuses an unknown key name with `key-unknown`, a harness that is not installed or logged in with `harness-not-connected`, and a malformed route with `route-malformed`. A harness route for any other role, or an effort on an API route of a role that takes none, is refused with `route-unsupported`. The script prints one line per role it spends on stderr, with the key name or the harness and the model. For a core step with tools the script serves a tool bridge of its own on a Unix socket in a new folder of mode 700 under `TMPDIR`, `bin/neptunia-mcp.ts` connects there in place of the core socket, and the script's step loop runs each call in its own process as a live turn does. A replay with `--answers-dir` answers every request of every role from the answer files, so nothing reaches a provider or a harness.

## Probes of the parts she needs

`createRouteWatches` in `src/subharness/route-watch.ts` probes her core, the analyzer and the memory writer, each on the route in force of its chain. A probe that fails moves the chain to its next route and probes that one at once, so she sleeps only when no route of the part answers. A part on the API gets one minimal request on its key, the request `/keys check` sends. A part on a harness gets the vendor's own status command, and then one one-word reply through that harness when it is logged in. The probes run at core start and every `memory.probeMinutes` (default `30`), and the memory writer's runs again at once after a refused writer run. An analyzer whose model is switched off and a memory session that is not `apply` pass with no request.

A failed probe while she runs pauses her with the part's reason, `core-down`, `analyzer-down` or `memory-down`, and the part's next passing probe lifts only that pause. When it lifts while another part's last probe failed, she sleeps again with that part's reason. A pause of the owner or `no-core-route` stays as it is. The header's line of the part says `error` while its last probe failed. A core whose model client the caller injected, as the test rigs do, probes no part on the API.

## The model selector

`/model` in the chat opens `ModelPicker` in `cli/model-picker.ts` and runs nothing until a choice needs it. The same bare word in a shell stays `/model show`, and every other `/model` line stays a command. The steps are category, role, provider type, source, model, effort and review. Main holds `core`, `drawing`, `speech` (shown as Voice), `memory`, `analyzer`, `vision`, `video` and `embedding`. Errand holds `scout` and `server`, Development holds `thinker` and `dev`, and `watcher` is a utility row under Development with no `models.development` key.

The selector reads `/model sources <role>`, whose JSON comes from `roleSources` in `src/subharness/model-capabilities.ts`. That read sends no model request and returns key names, never values. Each source row starts with its route name, and the selector commits that name as `--via`. Each source has a `code`, and any code other than `ok` is a disabled row with its reason. The codes are `not-installed`, `not-logged-in`, `no-key`, `provider-rejected` and `role-unsupported`. A direct-only role shows the three backends as `role-unsupported` without starting them, and an agent has no API row because an agent cannot run on the direct path. OpenRouter's models reach an agent through `opencode`, and only while `opencode` can run.

A model row says how it is known. `observed` came from the provider's listing now. `suggestion` is a name from `FIXED_MODELS`, which nobody checked against this account until the review saves it, and a typed name is `unknown`. The effort step offers keep, the model's default and the levels the installed binary's help lists. A backend whose help lists none offers keep and default alone. A direct-path source has no effort step, and `/model set <role> <model> --effort <effort>` stays the way to set its effort.

Enter on a disabled source lists the commands that repair it: `/subharness <backend> login`, or `/keys add <name>` and `/model set <role> <name>/<model>`. A key value goes through the chat's masked question and never enters the selector's state. After a success the selector reads the sources again and lands on the same source. A vendor login needs a terminal, so in the chat it answers the shell command to run, and the unfinished selection stays.

The review's Enter sends one `model.set`, the same checked command a typed line runs: for a model role its one route, `<key>/<model>` on an API source or `harness:<backend>/<model>[:<level>]` on a harness. A refusal stays on the review with its code and reason and saves nothing. An answer that belongs to an older revision of the selection changes nothing, so going back during a check leaves the new selection alone.

## Quick search

Quick search has its own `web.quickSearch.engine`, `web.quickSearch.model` and `search` key binding, independent of the analyzer. Neither setting has a default, so it stays off until `neptunia setup` or `/search engine` chooses an engine. The engines are `openrouter`, `brave` and `exa`, and nothing answers in place of the chosen one. `openrouter` needs `web.quickSearch.model` and uses the core key pool unless `search` is bound to a named extra key. It sends a model request with the search plugin, so the model and its cost matter. `brave` and `exa` need their service keys, and they condense a search for the selfreflection on `web.quickSearch.model` when one is set.

Use `/search` to inspect and change the engine, model and enabled state. Use `/model set search <name>/<model>` to put it on a key and `/keys check search` to check that route.

[Deep search](errands.md) runs through the scout. Its availability and credentials are separate from quick search.

## Service and module keys

`/keys service set <name>` prompts for a service value. Supported service names include `youtube`, `brave`, `exa` and `proxy`. The [setup guide](setup.md#optional-modules) links to the YouTube API instructions. `proxy` is the URL of the engine proxy, which `/proxy set` stores too and `/proxy on` puts in force (see [Proxy](proxy.md)).

`/interfaces set discord token` asks Discord's token through the masked question of its setup contract and writes it to `data/interfaces/discord/credentials.json`. A skill's setup contract declares its own secrets. Removing a platform's credentials does not remove stored memories from it.

Back up credentials with the complete persona, keep the backup private and do not commit credentials to Git. Key files are not encrypted by the engine.

Read the implementation in [key management](../src/keys/) and [search commands](../src/interface/commands/search.ts).
