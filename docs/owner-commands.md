# Commands

One slash command, `/nep`, with 19 top-level entries. Every reply is ephemeral (only the caller sees it). Channels, roles and users are picked from Discord's own pickers. Several options autocomplete: `set`/`unset` autocomplete `path`, `access grant`/`access revoke` autocomplete `command`, `model set` autocompletes `id` (the model ids in use), `route set`/`route remove` autocomplete `model`, and `memory restore` autocompletes `id` (the newest archive entries).

## Access

`/nep` is visible to every member from the start. Access is gated per operation at the moment a command runs, not through Discord's command visibility. Each command runs one named operation. Reading and changing are separate: `/nep memory show` runs `memory.profile.read`, `/nep memory affinity <user>` runs `memory.affinity.read`.

Owners (`bot.owners`) can always run everything. Everyone else needs a grant on the exact operation. `/nep access grant <operation> [role] [user]` opens one operation (e.g. `memory.profile.read`) to everyone (no role or user given), to a role, or to a user. A group name (e.g. `memory`) or `*` is accepted, but the grant is stored as the individual read operations that exist at that moment, one entry each: it never opens a write, and an operation added later stays closed until it is granted by name. `/nep access revoke` removes the target from one operation, or from every stored operation under a group or `*`. `/nep access list` shows each operation, who holds it, and where each grant came from when it was part of a group or `*` expansion. Without a grant, a non-owner gets an ephemeral "Not allowed" reply.

Owner-only operations (`access.*`, `diary.*`, `memory.private.*`, `memory.journal.read`, `memory.snapshot`, `memory.forget`, `memory.wipe`, `memory.archive.read`, `memory.restore`) are never opened by any grant, `*` included.

**Migration from the old command keys.** On the first start after the deploy that keyed access by operation, every stored grant is converted once: an old command key becomes the operation it ran; an old group or `*` becomes the read operations it covered; owner-only operations are dropped. A journal `system` record `access-migrated` lists what each old grant covers now. After the migration: `/nep access revoke * everyone`, then `/nep access grant memory.profile.read everyone`, and re-grant any other operation by name (check `/nep access list`).

## Status

`/nep status` shows a single card with the fields that matter most for a quick check: the bot's state (running or paused since when, plus a storage line, then the gateway connection and the uptime), long-running tasks (the emoji and GIF backfills, the GIF recache, the archive drain), then the core in three fields and the agents in two: `models.base` (one line per role -- voice, analyzer, extractor, vision, video, embedding -- with the role, the model, provider and latency; `models.base.byPurpose` overrides listed under their role), `keys.base` (for the main key, the simulator key and each `llm.keyByRole` key in that order -- the development agents' `OPENROUTER_DEV_KEY` as `development`, when the bot's `.env` carries it; the errand agents' `OPENROUTER_AGENT_KEY` has no line, their spend is in `costs.agents`: its limit with its spend, reset and whether BYOK counts, or "no limit" with the total used, followed by its usage: today, then the last 7 and 30 days from the bot's own figures -- for the simulator key, whose spend the bot never sees, this week and this month as the key reports them -- or, with `OPENROUTER_MANAGEMENT_KEY` set, from OpenRouter's activity records for every key), `costs.base` (today's requests per model role since 00:00 UTC, by cost: requests, prompt tokens with the cached part, completion tokens, cost and the average per request; the per-role figures persist in `data/usage.json`; the pictures are not here, they are the drawing agent's spend in `costs.agents`), `models.agents` (web, server, thinker, dev and writer with their OpenCode model; then drawing, with its model checked against the provider's listing) and `costs.agents` (per agent -- web, server, thinker, dev, writer, drawing -- its runs, input and output tokens and USD today, over the last 7 and the last 30 days: web, server and drawing from the task records in `data/guilds/<id>/tasks.jsonl` (the drawing agent's USD are OpenRouter's own cost figure for each picture), a run counting on the day it was queued, its tokens and USD on the day it ended, the same figures their daily caps `agents.<agent>.daily` read; thinker, dev and writer from the ledger (`agents.ledger.socket`, its `costs.agents` read: the thinker's turns, dev's and writer's attempts on development tasks, a run counting on the UTC day it started, its tokens and USD on the day it ended), with one more line under the thinker for its latest wave: its turns, its context mean and peak, its USD; the USD are OpenCode's estimate at each agent's price; with no ledger socket set, or a ledger that refuses or does not answer within 3 seconds, thinker, dev and writer show no runs and the rest of the field is unchanged), daily limits (requests, images, videos, recall, lookups, then `search: <engine>`: the `web.search.engine` in use, or `off` when no search can run), memory coverage per type (record, index, archive, profiles, server notes, channels, recent lines, participation: counts, span, percent), and speed over the last 24 hours (median, mean and count for reply with and without recall, recall steps, planner, analyzer batch, embedding flush; samples in `data/metrics.json`). Each role shows its own model (never another role's); no role falls back to another. The embedding role is probed with a one-input embedding request (using the `status.probe` text); without an embedding client the line says it was not checked. The `field` option shows that one field alone and runs only its checks (`field:limits` probes no model and reads no key). The `keys.base` field reads each key with one free GET request (one more per key for its activity with the management key) (`llm.probeTimeoutMs`, never counted against `llm.maxRequestsPerDay`); a failed read says why. Its costs are the ones OpenRouter reports: a BYOK request is billed by the provider and shows at OpenRouter's list price. The owner's `inner` field, after `costs.agents` and only while `features.innerLife` is on, shows the inner life in up to seven lines: the mode (`shadow` or `live`) and whether it runs or is stopped (and since when); the day's inner turns against `innerLife.caps.perDay`, with the chains they belong to; the day's real dollars, the dollars errands hold and `innerLife.caps.usdPerDay`; the day's public posts against `innerLife.caps.publicPostsPerDay`; the next wake (the earliest queued wake, intention due time or wait deadline, or the day's review time, UTC) or that none is known; the last inner turn's outcome and time; and the open intentions by status (pending, waiting, proposed). It is the data `/nep task inner action:status` reads. `field:inner` shows it alone; it is absent from the card with the feature off. A member granted `status.show` sees the card without `keys.base`, `costs.base`, `costs.agents`, `inner`, memory and speed.

## Granting skills to the persona

The persona's skills are the same operations behind `/nep` commands. Every skill is closed until the owner grants it with `/nep access grant <operation> user:@bot`, where `@bot` is the bot's own user. `/nep access revoke <operation> user:@bot` takes it back. `/nep access list` shows the persona's grants alongside everyone else's. A "yes" in chat never grants a skill: only the owner's command, authenticated by Discord, changes access.

A group name or `*` stores the read operations under it, one entry each, the same rule as for people. A write must be granted by its exact name.

**Carried over (current conversation only):** the persona's normal reply tags (`<msg>`, `<react>`, `<draw>`) count as `message.create`, `message.react.add` and `draw.create` in the current conversation without a grant. This is how the persona keeps talking: its reply is a batch of skill calls that pass the gateway because they are aimed at the conversation the turn belongs to. A grant opens the skill for other conversations too.

**Not grantable to the persona:** `memory.wipe`, `memory.private.purge`, `memory.forget`, `memory.private.forget`, `memory.restore`, `config.set`, `config.unset`, `model.set`, `route.set`, `route.remove`, `access.grant`, `access.revoke`, `bot.pause`, `bot.resume`, `inner.stop`, `inner.start`. These are the irreversible and administrative operations. A grant that names one of them (or a group or `*` that covers one) silently skips it. The persona also never changes rights that reach her: a grant or revoke she makes whose target is herself, everyone, or a role she holds is refused.

**In-turn tools:** `web.search`, `web.read`, `media.look` and `memory.search` are reads; with `features.coreTools` on, the persona's call of any of them runs inside her turn and its result comes back in the same turn (see [the tool loop](prompt-contract.md#the-tool-loop-featurescoretools)). None is open to her until granted by name (`/nep access grant web.search user:@bot`, `/nep access grant web.read user:@bot`, `/nep access grant media.look user:@bot`, `/nep access grant memory.search user:@bot`); `media.look` exists for her only while `features.coreTools` is on. A `*` or `memory` grant stored before they existed does not cover them.

**Self-owned operations:** `message.create`, `message.edit`, `message.delete`, `message.react.add`, `message.react.remove`, `draw.create`, `diary.post` and `diary.show` need only her own grant, not the requester's right (messages and drawings are hers). The bundled-author rule and the no-requester restriction still apply: no write when a turn answers several people, only a read when nobody asked.

## Memory commands

`/nep memory refresh kind:user <user>` rewrites a member's portrait now, ignoring the refresh-hours rail (not the daily cap). `kind:channel <channel>` and `kind:server` rewrite a channel's notes or the server notes (patterns, starters, in-jokes) from a fresh sample spread over recent days, the same request as the notes refresh in [Warmup](warmup.md#keeping-the-notes-current): the 50k token cap and `llm.maxRequestsPerDay` apply, the persona keeps talking, no whole history is read. A channel with no notes yet is refused with a pointer to `tools/warmup.mjs channels --channel <id>`; lore is rebuilt only by `tools/warmup.mjs server`. The warmup itself is not a command: it is `tools/warmup.mjs`, run with the bot stopped (see [Warmup](warmup.md)).

`/nep memory show` reads a member's stored profile: the compact summary or a specific section (character, style, relationship, affinity, aliases, interests, details, episodes, or the raw JSON). `/nep memory channel` shows a channel's stored notes or a table of all stored channels. `/nep memory server` shows the server-wide patterns, starters, in-jokes and self-facts.

`/nep memory forget` deletes a member's public profile, their private DM file, their voice queue items, their version history and their record and archive entries. Before deleting, it copies everything into a vault directory (`memory.vaultDir`, default `data/vault/`) and writes the member's id to `data/guilds/<id>/forgotten.json`. The engine never reads the vault back; to restore a member, copy their files by hand and remove the entry from `forgotten.json`. `/nep memory wipe` does the same for the entire server: it copies everything under the guild directory into the vault, then deletes all profiles, private files, channels, habits, lore, the journal, the record, the archive, the voice queue, versions, diary history and the recall trace.

`/nep memory journal` shows the persona's journal records for a UTC day, optionally filtered by kind (turn, action, memory, system, answer, inner). With `message` (a message id or link), it shows the full record of the turn that posted that message: trigger, outcome, posted ids, skill calls and the stored think. The other options are ignored when `message` is given. `/nep memory archive` shows archived items, optionally for one member or one kind. `/nep memory restore` puts an archived item back into hot memory (the `id` autocompletes from the newest entries). `/nep memory snapshot` copies `data/` to a timestamped directory for the measurement tools.

`/nep memory private show` reads a member's private DM memory. `/nep memory private forget` deletes only the private file; the public profile stays. `/nep memory private purge` deletes the private file and also bulk-deletes the bot's DM messages to that member (up to `private.purgeMaxMessages`).

## Member commands

`/nep pings`, the `/nep task` group (but `/nep task intent` and `/nep task inner`, owner commands) and `/nep memory search` are the commands every server member may run without a `bot.access` grant. `features.memberCommands: false` restricts them to owners.
