# Media and search

The persona uses descriptions of media as durable conversational evidence. It does not need to watch the same image again on every turn. A description lives on its item's row of `media` and nowhere else.

## Descriptions and originals

A saved description is reused after a restart or after the cache's cap retired its row: `getMediaDescription` reads it from the retired row, and the describer writes it back with no request. An explicit rewatch replaces the entry with its new answer. A failed refresh keeps the successful description and stamps it with the failure. While the request of a picture, a GIF, a video or a voice message is out, its cache entry is `pending`, and a stale description that is refreshed keeps its text under the mark. A pending entry is never shown as a description and never stops a second look, and a request that caches nothing takes the mark away. At the engine's start `recoverRequestArchive` in `src/memory/db/request-archive.ts` settles every pending entry a stop left. An entry with no text becomes a miss with the reason `interrupted`, so the line shows that the item could not be looked at, through `labels.transcript.videoReason.interrupted` for a GIF or a video, and the describer's handling of a miss applies. An entry that holds a description keeps it, loses the mark and is stamped with the failure, as a failed refresh is.

## How a picture is described

`describe` in `src/memory/describe.ts` sends the picture to the `vision` role as a data URL under the system message of `prompts['describe/picture']`. The caption is the whole answer, every line joined into one line with single spaces. Its length is `PICTURE_DESCRIPTION_CHARS`, 750 characters. A still sticker and a still custom emoji take the same path, and the request shows their captions once each in the legend `<media>`, never in the line ([prompt contract](prompt-contract.md#the-frames-blocks)). The prompt asks for what is visibly there, the legible words and the regions that are unclear.

A GIF's description takes `GIF_DESCRIPTION_CHARS`, 1000, a video summary `VIDEO_DESCRIPTION_CHARS`, 5000, and an audio summary `AUDIO_DESCRIPTION_CHARS`, 3000. A second look takes the length of its media. Each prompt learns its length through `{{maxChars}}`. The describer cuts no answer. An answer over its length goes once to the summarizer in `src/behavior/summarize.ts`, one `analyzer` request with the purpose `summarize`, and its result is stored whole on one line, as the answer is, even when it is still longer. A failed summary keeps the answer whole. `plainDescription` in `src/memory/plain-description.ts` then makes the final text of a picture, sticker, emoji, GIF or video description and of a second look plain, before it is cached or returned. It drops markdown emphasis around words, backticks, a heading mark and a list bullet at a line start, and turns an em dash into a comma. A lone asterisk and an underscore inside a word stay.

A GIF is watched as a short clip through the prompt `describe/gif`, else `describe/video`, and never described from a still frame. An animated custom emoji or sticker is watched the same way from its `animationUrl` and stored under its own item id. It never enters the GIF library, which holds GIF embeds and attached GIFs. The fetcher takes a PNG as an animation when its bytes hold an `acTL` chunk, and hands it to ffmpeg as an APNG. A still PNG fails as `download`. `{{seconds}}` of `describe/gif` is the length of the watched clip, to one decimal at most. `fetchGif` in `src/media/fetch-video.ts` reports that length and the whole GIF's length. A GIF longer than the clip, at most 15 seconds, adds `labels.gifCut` with `{seconds}` and `{total}` to the system message after a blank line. Its answer is three labelled lines, `reaction`, `action` and `text`, joined and stored as one text on one line with the labels intact. The transcript, the answer of `media.find` and the candidate list of the media pick show that text whole, through `labels.gifs.entry` in the two lists.

Every attachment comes from a fresh address, because a platform's attachment address is signed and expires. Before each download of a picture, a GIF, a video, a voice message or a text file, the core reads the attachment's message again through the interface and takes its address, the same read that posts a library GIF. A picture is then downloaded from that address and never from its stored preview address. When that read fails, the stored address is fetched. An attachment with no message id is fetched by its stored address. A link, an embed, a sticker and a custom emoji are fetched by their stored address. A watch that fails stores a miss with its reason: the fetcher's own reason, `llm` for a failed request, `empty` for an empty answer, or `filter` or `cut` for an answer cut short twice. The GIF is watched again after `media.video.errorRetryMinutes`, default `60`. Until then the transcript shows it as `transcript.gifNotWatched` with its name and the reason, worded by `transcript.videoReason` where that map holds the code. While GIFs are not watched, or the daily request cap is spent, nothing is requested and nothing is stored. A picture, a still sticker or a still emoji whose description fails stores a miss by the same codes: `download` for a refused status or type, a network fault or a failed body read, `timeout`, `size` for a file over the vision limit, `llm` for a failed request, `empty` for an empty answer, and `filter` or `cut` for an answer cut short twice. Whatever its reason, the picture is described again after an hour, and until then the transcript shows it as `transcript.imageNotSeen` with the reason, worded by `transcript.videoReason`.

The vision model is told nothing of who she is. A description names what the picture shows, never her.

The engine does not promise to download every attachment it encounters. Diary originals are preserved under `data/media/`, with database references and checksums. Every file of the owner's command line chat, in both directions, is copied to `data/media/cli/` by `src/chat/kept-media.ts`, and the `path` of its `media` row names the copy ([cli](cli.md#kept-files)). A GIF of the library keeps every link it was seen under in the `extra` of its `media` row, and a link GIF keeps `fileUrl` beside them, its direct media address. That address is the animation address of a GIF site's embed or of a plain `.gif` link, and never the page link, which answers a page. Discord's adapter takes the provider's own video address first, since it is unsigned and outlives the message, and Discord's proxy address only when the embed has no other. An attached GIF keeps no `fileUrl`, because an attachment's address is signed and expires. When a message shows a library GIF that has no file, the media prefill downloads the file once into `data/media/gifs/`, named by its content hash, through `src/media/gif-files.ts`. A link GIF's file comes from its `fileUrl`, and an attached GIF's from the address of the message that shows it. An edit that brings a GIF does the same, and so does the history backfill for every GIF it reads. A failed download leaves the row without a file, and the GIF's next sighting tries again, a link GIF from its `fileUrl` and an attached GIF from that sighting's address. The file is a spare copy, and the core's start downloads nothing. `path` on a `media` row is null or a file under `media/`. A GIF's vector is the ordinary media vector of its row's description, which the media embedding writes for every library row, whether a line links it or not. A cached description, an external URL and a preserved original are different things when preparing a backup.

## Answers the provider cut short

An answer whose finish reason is anything but `stop` is no description. The provider's content filter ends an answer with `content_filter`, and the output cap ends it with `length`, often after the model repeats itself. Such an answer is never cached, stored or returned, and it never replaces a description. The describer sends the same request once more, and a second answer that ends normally is the description. A second cut answer is a miss with the reason `filter` for the content filter or `cut` for any other finish, and the retry rule of a miss of that kind applies. An older description stays and stays shown. A picture with no description shows as `transcript.imageNotSeen` with the reason, worded by `transcript.videoReason`. A second look cut twice fails with its reason, and `media.look` returns the code `error` with that reason. The second request that brings a description to the English standard follows the same rule, and a cut second answer leaves the first one standing. Each cut answer writes one `describe: cut` log line with the kind of media and the two finish reasons, never the text. This covers a picture, a sticker, an emoji, a GIF, a video, a voice message, an audio file and every second look.

## Available abilities

A voice message or an audio file reaches the describer on the `video` role through the prompt `describe/audio`. `fetchAudio` in `src/media/fetch-video.ts` carries it as a short clip, packaged by `ffmpegAudioArgs` in `src/media/video-sites.ts`, and `audioPart` in `src/memory/describe.ts` puts it in the request. `fetchAudio` takes an answer of type `audio/*` or `video/*` and refuses any other, so a page a CDN answers with never reaches `ffmpeg`. The clip's black picture stops with the sound, at most a tenth of a second past it. A file refused for its size is not tried again, and a passing failure is tried again after an hour, with the cause kept on the cache entry. A text file's text form is its own words. A file over `TEXT_FORM_CHARS`, 2000 characters, goes once to the summarizer with the prompt `summarize/text`, and the retelling is its text form. A transcript and what she voiced are quoted speech as a whole, so the script check of a description does not apply to them and they stay in the language spoken.

`draw.create` builds the drawing prompt from `prompts/draw.md`, her scene and, for a picture she is in, the text of `prompts/appearance.md`. The appearance text sets her face, hair, eyes and build, and the scene sets her clothes, pose and expression. A picture she is in goes to the `drawing` role with `appearance.png` of the data folder as its reference picture. With no such file it goes without a reference, and a picture she is not in never takes one.

A picture she draws with `draw.create` is looked at once it is made. A posted picture is described through `describe` as the attachment it became, from its own bytes, so the caption is cached under the attachment's id and her chat window shows it on the next turn with no second request. A picture staged for a diary entry has no message yet. It is described from its bytes with the same prompt, and nothing is cached. The description comes back in the call's result. When the look fails, the call still succeeds and the result says the picture could not be looked at. Each `draw.create` adds one request of the `vision` role.

The media she made carry marks in the `extra` of their `media` row: `made` with the value `self`, and on a picture `depicts`, the person ids of the people it shows. The vision helper describes a picture without knowing who is in it, and the marks tell her it is hers and whom it shows. A picture from `draw.create` or the owner's draw command is marked with her own person when `self` is true and the people of its `people` argument. Her `said` line carries the marks into memory, which writes them on the line's items whether the line or the posted message's echo came first. A voice message she speaks is marked with her own person. A diary picture carries its marks into the entry's row and the chat line its mirror makes. A GIF, an emoji, a sticker or a link she reposts gets no mark. When two people merge, the ids in `depicts` move to the person who stays. The tags show each person but her by `@` and the person's handle, the form a person argument of a tool takes on every interface, so a rename changes nothing in them.

Drawing and voice use their configured model roles and credentials. `ffmpeg` supports audio conversion and video preparation, and `yt-dlp` retrieves supported videos. The optional YouTube Data API key supplies metadata rather than vision. Configure it through [setup](setup.md#optional-modules).

The turn's senses report which abilities are available. A configured credential alone is not proof that a remote provider is reachable. Tool failures return to the turn so the persona can decide how to proceed.

## Search

Three paths reach the web, and each has its own availability. Turning quick search off changes neither of the other two.

Quick search is the core's `web.search`, in [src/web/lookup.ts](../src/web/lookup.ts). It runs on the one engine in `web.quickSearch.engine`, which is `openrouter`, `brave` or `exa`. No engine is built in, so it stays off until `neptunia setup` or `/search engine` chooses one. The tool result says why it is off: `no-engine`, `no-key` for `brave` or `exa` without its key, or `disabled` by `web.quickSearch.enabled`. When the chosen engine fails, the result names the engine and the cause, `timeout`, `rate-limited` or `credentials` among them, and no other engine answers in its place. The `openrouter` engine sends one request with the web plugin, which sets no `engine`, on the analyzer under the purpose `quick-search`.

Page reading is `web.read`. [src/web/fetch-page.ts](../src/web/fetch-page.ts) checks the address of the link and of every redirect against private ranges, caps the size and refuses unsupported content. The text she reads names the address the page ended at, on an empty page too, and a user name or password written into a link reaches neither that text nor the cache. The read stays in the media cache under `page:<hash of the address>` until a later read replaces it, and past `web.links.readCacheHours` a `web.read` of the address fetches the page again. It is the link's text form: `readLinks` and `cachedReads` in [src/web/lookup.ts](../src/web/lookup.ts) answer it for every link to that address, in place of the preview and with no fetch. A page text over 4000 characters goes once to the summarizer with the prompt `summarize/text`, and the read holds the retelling, which her result names as one with `tools.tools.read.retold`. A transcript shows the read whole on one line.

No text she reads is cut silently. Where a bound stays, a text over it goes once to the summarizer, one `analyzer` request with the purpose `summarize`, and the retelling stands in its place. A link's excerpt over `LINK_EXCERPT_CHARS`, 1000, is retold before it is cached. A search snippet over 400 characters in a `web.search` result is retold, every snippet of one search side by side, and the result's title and link stay whole. A quick search's summary note over 900 characters is retold, on every engine. A lookup's extract over `context.recall.extractChars` is retold once before `<recall>` and the journal keep it. An avatar's description over 200 characters is retold as a picture's, the vision answer joined on one line. The page fetcher and the Exa engine return their text whole, and each reader retells it once for its own bound. A text file attached to a message over 10000 characters is retold, and its line reads `transcript.filePreviewRetold`. A retelling still over its bound stands whole, and a failed request leaves the text whole. A link preview's title and description and a URL in a message's text reach the core whole, and a recorded link keeps its URL and site whole.

Deep search is an errand for the scout, which searches with its harness's own tools: the OpenCode route uses its `websearch` tool on the route's key.

When only deep search is available, the persona can use it directly. When both are available, the model chooses the appropriate tool and can follow an unhelpful quick result with deeper work. See [keys](keys.md#quick-search) for routing and [errands](errands.md) for the scout.

Implementation entry points are [src/media/](../src/media/), [src/tools/operations/](../src/tools/operations/) and [src/memory/db/](../src/memory/db/).
