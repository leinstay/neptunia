# Configuration

Every setting lives in `config/config.json` with its default value. A deployment overrides what it needs in `config.local/config.json`, which is deep-merged over `config/config.json` at startup and on every file change. Plain objects merge key by key, and arrays and scalars in the local file replace the base value whole. `src/config/files.ts` says which file the loader reads, and `src/config.js` and `src/hot.js` read it.

Both files reload without a restart. Code reads `hot.config` at the moment of use, so an edit takes effect on the next request. A file that fails to parse (half-written JSON, an editor temp file) is ignored: the previous good value stays live and the error is logged. At startup, invalid JSON still throws so a broken deployment fails fast.

Any string value in the merged config may hold `${env:NAME}` (`NAME` is letters, digits and `_`, not starting with a digit). After the merge, each reference is replaced with the variable's value from `.env`, so a credential can stay in `.env` while the config holds only the reference. An unset variable becomes an empty string and is logged once (`config: env ref unset`). `/config set` keeps the reference in `config.local/config.json`, and every reload resolves it again.

The tables of this document are generated by `tools/config-doc.mjs` from the settings schema, `src/config/schema.ts`, which holds every key with its types, its default, one line of text and the module that reads it. Its entries live in `src/config/schema/<section>.ts`. A new key gets an entry there and in `config/config.json`, then `node tools/config-doc.mjs > docs/configuration.md` writes this file again. `tests/config-schema.test.ts` holds the defaults equal to `config/config.json`, `tests/config-check.test.ts` checks that each reader module names its key, and `tests/config-doc.test.ts` fails while this file differs from the generator's output.

`/config check` in the owner's chat and `neptunia doctor` check `config.local/config.json` against the schema and name each key the schema does not know and each key whose value has a type the key does not take (`src/config/check.ts`). The core starts on such a file all the same.

## Where the private files live

By default everything sits in the checkout: `config/` and `prompts/` (tracked), your `.env`, `config.local/` and `prompts.local/`, and the `data/` directory the bot writes to. `config/` holds `config.json` (the settings), `labels.json` (the wording code inserts, see [Prompt contract](prompt-contract.md#labels)) and `tools.json` (the tool texts), and `config.local/` holds the same three files for a deployment, each deep-merged over its tracked file, plus `interfaces/<name>.json`, which `neptunia interface run <name>` lays over the interface package's own `config.json`. Two environment variables move the private parts out of the checkout:

| Variable | Default | What lives there |
|---|---|---|
| `NEPTUNIA_PRIVATE_DIR` | the checkout | `.env`, `config.local/`, `prompts.local/`, `clients.json`, `clients/`, `cli/` (the chat's picture and history, see [The neptunia command](cli.md)) |
| `NEPTUNIA_DATA_DIR` | `data/` in the checkout | everything the bot writes: `guilds/`, `state.json`, `usage.json`, `metrics.json`, caches |

Set them in the process environment (for example `Environment=` in the systemd unit), not in `.env`: the bot reads `.env` from the private directory, so it needs to know that directory first. A relative path is resolved against the checkout. An edit to a file in `config.local/` or `prompts.local/` inside the private directory still reloads live. The tools read the same two variables; `--data` overrides the data path. At start the bot logs the three resolved directories (`index: paths`). `deploy/neptunia-bot.service` shows the recommended layout.

## The old layout of the private files

A private directory laid out the old way keeps its settings in `config.local.json` and its labels in a flat `prompts.local/labels.json`, with no `model` and `owner` sections. The engine reads both as it reads the new files and logs one warning per start that names `tools/config-files-move.mjs`. A directory with a file at both its old and its new place refuses the start with a message that names the same tool.

`node tools/config-files-move.mjs --private <dir>` says what it would move, and `--apply` moves it. `config.local.json` goes to `config.local/config.json` byte for byte. `prompts.local/labels.json` goes to `config.local/labels.json`, split by the checkout's `config/labels.json`: a key the tracked file holds under `owner` goes to `owner`, every other key to `model`. When a file sits at both places with the same content (the labels compared after the split), the run deletes the old copy. With different content it refuses, names the old file and changes nothing. A second run finds nothing to do.

## Clients and their tokens

`clients.json` in the private directory names every client that may connect to the core's socket, and `clients/<name>.token` holds each client's token. An entry has the client's `kind` (`interface`, `cli`, `plugin` or `agent`), the `iface` an interface's events must carry, the `tokenFile` relative to the private directory, and `permissions`. The core reads both files at every envelope (`src/interface/principals.ts`), so a change applies at once and a rotated or revoked token closes that client's link. Without `clients.json` the core makes one token at start for the interface it runs in its own process, and nothing else connects. A `clients.json` that is not valid JSON lets no client in. See [Interfaces](interfaces.md#clients-and-principals).

An entry may also carry `boardRoles`, the client's roles on the task board: any of `owner`, `reviewer`, `worker`, `scheduler`, `persona`, `watcher` and `errand-runner`. The board reads them at every call (`src/board/board.ts`). An entry without `boardRoles`, a name outside that list and a client absent from the file get no right on the board. See [The core](core.md#the-task-board).

The owner's `neptunia` chat is the client `cli` of kind `cli`, which runs every command with the owner's rights. An interface client sends no command: the link refuses its `command.requested` whatever its `permissions` hold. A client of kind `agent` is a development agent of the task board: it says hello under `agent`, sends only the board's `task.*` commands (`neptunia task`, see [The neptunia command](cli.md)), and the board lets it do what its `boardRoles` allow. A `task.*` command of the `cli` client goes to the board too, under the client's own `boardRoles`. The board's builtin principal `persona`, which her board tools call as, holds the role `persona` alone, and an entry named `persona` adds nothing to it.

`tools/client-token.mjs` writes both files, at mode `0600`, in the private directory `NEPTUNIA_PRIVATE_DIR` names. It never prints a token.

| Command | What it does |
|---|---|
| `node tools/client-token.mjs add <name> --kind <kind> [--iface <iface>] [--permission <p>] [--roles <role>,<role>]` | Makes a token and the client's entry. `--kind interface` needs `--iface`. `--permission` may repeat. `--roles` writes the comma list as `boardRoles`, with any kind, and a role outside the board's list writes nothing |
| `node tools/client-token.mjs rotate <name>` | Writes a new token over the old one |
| `node tools/client-token.mjs revoke <name>` | Removes the entry and the token file |

The token file belongs to the user the client runs as: `chown` it after `add` and after `rotate`.

## Keys that moved

The persona's skills are tools in the settings. `src/config-moves.ts` holds the old names as an ordered list, and `src/config.js` applies it to the private settings file before the file is laid over `config/config.json`, so an old key still sets the value of its new name. Each load that moves a key logs one warning with the counts. Where both names are set, the new one wins.

| Old key | New key |
|---|---|
| `skills.*` | `tools.*` |
| `features.skills` | `features.tools` |
| `features.skillsDiscovery` | `features.toolsDiscovery` |
| `bot.access."skills.describe"` | `bot.access."tools.describe"` |
| `bot.access."task.run"`, `"task.status"`, `"task.read"`, `"task.resolve"`, `"task.cancel"`, `"task.list"` | `bot.access."errand.run"`, `"errand.status"`, `"errand.read"`, `"errand.resolve"`, `"errand.cancel"`, `"errand.list"` |
| `bot.access."intent.set"`, `"intent.update"`, `"intent.cancel"`, `"intent.list"` | `bot.access."intention.set"`, `"intention.update"`, `"intention.cancel"`, `"intention.list"` |
| `agents.opencodePath`, `toolResultChars`, `keepFilesHours`, `recentLines`, `maxOpen`, `resultMaxChars`, `unreadShown`, `resultRetrySeconds`, `resultCooldownSeconds` | the same names under `errands.*` |
| `agents.<name>.search.provider` | `agents.<name>.searchProvider` |
| `llm.helperTimeoutMs` | `llm.analyzerTimeoutMs` |

Seven keys have no reader any more and are dropped: the grants `bot.access."memory.refresh.channel"`, `"memory.refresh.server"` and `"memory.refresh.user"`, `agents.maxDownloadBytes`, `agents.thinker.contextLimit` and `contextHard`, and `agents.ledger.socket`. A section a dropped key leaves empty goes with it. The load log line counts them as `dropped` beside `moved` and `shadowed`.

`node tools/config-migrate.mjs --dry-run` prints each move for the private settings file (or `--file <path>`), each dropped key as `<path> dropped (no reader)`, and `--apply` writes the result into the file. A second run finds nothing to move. `--dry-run --compare-with <config.json>` reads the settings the moves touch twice, once the old way over the given `config.json` and once through the current readers over this checkout's, and prints `equal: <n>, differ: <n>` with one line per difference. It exits 1 on any difference. `--self <id>` names the persona's user id when `bot.self` is not set, so the grants can be compared.

The owner commands that edit the private settings file (`set`, `access grant`, `access revoke`) apply the same moves to the file before they read it, so a write never leaves a key of an old name beside the new one.

The tool texts moved too: `prompts/skills.json` is `config/tools.json`, and a deployment's `prompts.local/skills.json` is `config.local/tools.json` with the entry `skills.describe` renamed `tools.describe`. The `skills` section of `prompts.local/labels.json` is the section `tools`. The errand and intention names changed in the same layer: the ten tool entries `task.*` and `intent.*` of the tool texts are `errand.*` and `intention.*`, and in `labels.json` the section `tasks` is `errands`, the trigger `task` is `errand`, the note `task-missing` is `errand-missing`, the reason codes `no-task`, `task-ended` and `wait-without-task` are `no-errand`, `errand-ended` and `wait-without-errand`, and the placeholder `{task}` is `{errand}` in the texts that carry it. `node tools/tools-file-move.mjs --dry-run` and `--apply` do all of it, read `--dir` or `NEPTUNIA_PRIVATE_DIR`, and change no file when any part is refused. The engine refuses to start while `prompts.local/skills.json` exists.

## Rails

Two hard rails that must stay on:

- **50 000 tokens per request** (`llm.maxRequestTokens`). Every request the bot sends is budgeted against this cap. The prompt builder trims sections by priority to fit.
- **Daily request cap** (`llm.maxRequestsPerDay`, default 5000). Every model request counts (requests on every model role, probes, tools, hedged duplicates).

## `models`

Three groups, the same three the status card shows (`/status full`). Each role is set independently with its own default, so changing one never moves another.

- **`models.base`**: the bot's own requests. The core decides and speaks as the persona; each other model role gathers, describes, extracts or finds.
- **`models.errands`**: delegated agents. Each runs its own OpenCode loop as a separate process. See [Errands](errands.md).
- **`models.development`**: agents that work on the repository, not on the persona's behalf. The engine only describes them and shows their spend.

### `models.base`

<!-- settings: models.base -->

A role set to `false` has no model. Its tool calls (`media.look` for `vision` and `video`, `draw.create` for `drawing`, `voice.say` for `speech`) go to the core model when the core declares the role's ability in `models.abilities`, and answer `ability-unavailable` otherwise. `/status` lists the role as failing and `neptunia doctor` warns about it. `null` or a missing key is the role's default model. The same route applies while a role is failing globally (see [Media](media.md#when-a-model-role-is-down)).

### `models.abilities` and `models.byPurpose`

<!-- settings: models.abilities -->

Only the core model's list in `models.abilities` is read, by `src/tools/gateway.ts#abilityRoute`, when a tool role is down. A core model without an entry has `text` only, so a down tool role answers `ability-unavailable`. A deployment whose core reads pictures gives its core model the list `["text", "imagesIn"]`.

## `llm`

<!-- settings: llm -->

### Provider routing resolution

For one request the provider is resolved in order: a per-call pin, then the longest matching `providerByModel` key for the request's role (`<prefix>@<role>`), then the longest matching role-less key (`<prefix>`), then `llm.provider`, then nothing. A role-specific key always beats a role-less key for the same model. A route may carry `"byok": true` (never sent to OpenRouter): an answer OpenRouter served from its own capacity instead of your provider account fails without a retry.

## `agents`

The settings of one agent live in its profile, `agents/<name>/profile.json` (see [the agents folder](../agents/README.md)). A deployment overrides a setting under `agents.<name>` of `config.local/config.json`, and `agentSettings(name, config)` in `src/agent-runner/profiles.js` lays the override over the profile, a nested object merged key by key. The core, the agent runner and the dispatcher all read an agent's settings through it.

<!-- settings: agents -->

The keys of a profile and the values the shipped profiles carry:

| Profile key | Default | What it does |
|---|---|---|
| `enabled` | `false` for `scout` and `server` | Runs the worker. Workers only |
| `cost` | `scout` and `server` `{ "input": 2, "output": 6 }`, `thinker` `{ "input": 4, "output": 20 }`, `dev` `{ "input": 2, "output": 10 }` | Model price (USD per million tokens) for OpenCode's estimate and the spend figures |
| `socket` | `"/run/neptunia-agent-scout/sock"`, `"/run/neptunia-agent-server/sock"` | Unix socket of the runner. Workers only |
| `out` | `"/var/lib/neptunia-agent-scout/out"`, `"/var/lib/neptunia-agent-server/out"` | Directory for output files. Workers only |
| `limits` | `scout` `{ "steps": 25, "seconds": 300 }`, `server` `{ "steps": 20, "seconds": 120 }`, `thinker` `{ "steps": 400, "minutes": 60 }`, `dev` `{ "steps": 300, "minutes": 60 }` | Caps of one run |
| `daily` | `{ "tasks": 40 }` for `scout` and `server` | Tasks per day. Workers only |
| `searchProvider` | `"exa"` for `scout`, `null` for `server` | Web search provider, `exa` or `parallel`. Workers only |

The thinker and the dev agent run outside the engine; the bot only shows their spend on the status card.
